# 0011 — Immutable attachment processing and reservations

Date: 2026-10-03. Status: Accepted for the authorized Module 07 implementation; lifecycle acceptance remains incomplete.

## Context

Signed PUT and multipart capabilities are reusable until expiry. HEAD/ETag checks against staging cannot establish the bytes later served. Both first-class profiles need principal/project quota reservation, draft associations and crash-safe processing. SECURITY §§99–105 requires current authorization, actual-byte validation, isolation and truthful scanning state. PERFORMANCE §38 places large checksums and scanning outside ordinary synchronous API requests. Module 09 scheduling remains held, and Module 07 audit work remains suspended.

## Decision

Reserve a bounded maximum byte count and one outstanding-intent slot atomically against a project counter and a global principal counter. Limits are server-owned policy, never client input. An additive intent-details table binds the existing upload intent to a safe filename, distinct staging/final keys, intended existing Issue/comment or explicit Issue/comment draft identity, optional provider version and a fenced processing lease. Existing legacy intents without details remain unsupported by the new processing path; historical migrations and existing attachment target constraints are preserved. The additive accounting migration counts legacy finalized actual bytes as used and every other legacy intent maximum/slot as reserved; unsupported legacy rows cannot silently escape quota. Reconciliation must verify physical cleanup/adoption before releasing their counters.

Finalization records processing intent before a bounded background handler claims a persisted lease. That handler streams staging into a create-only backend-owned final object, then validates and hashes the actual immutable final snapshot. Its backend-authored intent metadata permits safe crash resume. A stolen/expired lease cannot commit verification. Successful verification atomically replaces the maximum reservation with actual used bytes; it does not establish scanning or release. The canonical immutable version is `sha256:<digest>` paired with the final key; the actual provider version remains separately nullable, matching unversioned S3 providers without inventing a provider version.

An Issue draft has its own opaque identity; a comment draft additionally names an existing same-project Issue. Existing content associations use same-project foreign keys. Unlinked verified content remains in intent storage until a future atomic content transaction consumes that exact association and creates the existing attachment row. Upload IDs are the stable reference identity; filenames and reusable storage URLs are never canonical references in Markdown.

No public route can invoke the primitive without current authorization, reservation and state checks. Files remain explicitly unscanned/quarantined until the scanner/release policy is implemented. Rejected objects retain ownership for resumable cleanup; a concurrent verification failure never deletes a final object another worker is using. Expired unverified cleanup requires the intent expiry plus a 300-second capability grace and a fenced lease. It deletes both owned keys, checks absence and releases the reservation exactly once, retaining tombstone keys so late PUTs can be removed again. Verified-unlinked orphan cleanup and multipart cleanup remain incomplete. Module 07 may implement handlers/contracts; this decision does not authorize Module 09 scheduling, product deployment, audit resumption or SPA work.

## Alternatives and consequences

Staging HEAD plus a reusable signed URL leaves a TOCTOU hole. S3 versioning is not portable across the selected profiles. Buffering or hashing large uploads in ordinary API requests violates the processing boundary and scales poorly. A shared create-only final key with actual-final-byte inspection supplies a portable invariant and permits retries at the cost of a second stream/read and explicit processing state.

The additive tables avoid rebuilding the foundational upload/attachment tables and preserve upgrade data. Quota counters require both-dialect rollback, concurrent reservation, duplicate submission, lease fencing and accounting proofs. Public authorization, attachment linking, scan/release, media delivery and physical cleanup remain separate unfinished Module 07 batches. Focused security/consistency/performance review and actual storage race evidence are recorded in [Module 07 progress](../plan/progress/07-content-and-attachments.md) and [storage evidence](../plan/evidence/07-storage-validation.md).

## Multipart refinement — 2026-10-03

Select and persist direct versus multipart transfer at reservation. Multipart records store a server-owned uniform part-size/max-count plan, provider session identity and a bounded catalog of client receipts. Receipts are claims, not verification: completion freezes the catalog under a fenced lease, compares actual completed staging metadata/size with its bounded total, and background promotion still validates/hash-streams immutable final bytes before accounting. Part receipt updates use an expected catalog revision; clients resume after conflicts by reading the current catalog. Part capabilities only use the persisted owner/project session and never accept a client-authored provider ID/key.

Database mutations and provider operations remain separate. Persist a creating marker first, then register the returned provider ID under the lease. Known failed creations are aborted; ambiguous creation without a recorded provider ID cannot safely create another session or release quota. The current native blob port has no multipart discovery operation, so explicit provider discovery/reconciliation is required for that crash window; full 07.3h orphan acceptance remains incomplete. Completed staging metadata permits recovery after provider completion succeeds before database completion, but never substitutes for immutable final verification or scanning. Abort/rejection retain the reservation until physical cleanup; known multipart sessions are aborted before owned objects are deleted. No new scheduling/workflow or audit scope is authorized.

## Scanner/result refinement — 2026-10-03

A trusted injected scanner consumes only backend-owned immutable final bytes in an independently callable bounded background handler. Core checks complete stream consumption, exact stored size and SHA-256 before accepting its verdict, and persists a result bound to intent/project, attempt lease, immutable identity, policy version and bounded engine/signature metadata. Client callbacks cannot supply a clean verdict. Missing scanner leaves unscanned/quarantined; unavailable/failed/partial/mismatched scans never release content.

Scan claims/results/release use the same fenced intent lease and current authorization inside both database profiles, without provider work in transactions. A single mutable latest-result row is operational policy state, not audit history; suspended audit scope remains untouched. Clean result persistence and explicit release are separate conditional transitions, so a crash or permission loss between them leaves clean-but-quarantined content. Release requires the current scan policy and exact immutable result identity. Infected content is rejected; transient failures remain quarantined, and used quota is retained until later physical cleanup. The stronger current Core policy never releases unscanned files.

This hook does not supply a scanner implementation, run malware detection, schedule work, or prove release acceptance. Synthetic scanner tests must be labeled as such; 07.3f remains partial until an actual scanner/result integration is verified. Module 09 dispatch, 07.2e audit and SPA stay held.

## Cleanup/reconciliation refinement — 2026-10-04

A bounded internal project-local page selects at most 20 supported expired reserved/released intents, excluding live leases and verified used files. Physical cleanup remains fenced and accounting releases exactly once after absence checks. The state/expiry/UUID keyset reuses the existing expiry index; tombstones remain available for subsequent late-write sweeps. This is count/concurrency bounding, not a claim that every provider request has a hard deadline.

Unknown multipart creation may use a trusted exact-key discovery/abort/absence port with a 30-second Core timeout. Missing or malformed/truncated/failed discovery never authorizes quota release. The ambiguous creation marker is retained on released tombstones so later sweeps repeat provider discovery; a one-time discovery cannot prove that an older provider operation will never complete late. Both selected storage compositions now supply the shared bounded reconciler through native R2 header-signed S3 or Node AWS SDK discovery. Absent/failed discovery continues to retain reservations. Synthetic callbacks prove Core fencing only; actual R2 S3, native workerd/remote R2 and real local SeaweedFS acceptance are recorded separately in the lifecycle evidence. No new database migration, dispatcher, audit or deployment is implied.

## Form consumption refinement — 2026-10-04

Explicit form draft identity binds nonempty upload answers to the submitting owner/project. Existing attachment rows consume only finalized/used/current-clean-scan/ready issue-draft intents with no active processing lease and permitted field filename extensions. The upload intent ID becomes the attachment ID, preserving opaque deterministic Markdown references. A unique upload-intent link prevents multiple content consumption. Issue, attachments, original structured answers/version, number allocation, timeline, outbox and receipt commit together on both dialects.

Consumption promotes the draft association to the created issue and increments upload revision without changing immutable final bytes or used quota. Processing thereafter inherits current parent authorization. PostgreSQL follows project-first locking and locks intent/detail/result rows; D1 per-file scalar NOT NULL witnesses force rollback on failed eligibility, including a race after pre-read. Exact receipt replay precedes association checks and a concurrent winner is rechecked before a changed-draft error. The existing schema is sufficient; no migration or stored derived content is added.

Synthetic clean scan fixtures verify the consumption boundary, not malware detection. Actual scanner acceptance, isolated delivery and verified-unlinked retention/cleanup remain distinct unfinished acceptance. Audit/Module 09/SPA holds continue.

## Isolated delivery refinement — 2026-10-04

Deliver released bytes through an explicitly selected media origin and backend-authorized streaming GET/HEAD. No private signed download URL is issued. All file types initially download as octet-stream with safe disposition, no-store/nosniff/sandbox/no-referrer; public access requires current visible public parents, and private access requires current bearer/active Staff membership and shared read permission. Recheck the exact attachment/scan/association snapshot and authorization after acquiring storage, cancel on denial, and bound stream size, pull buffering, idle time and total lifetime.

The media hostname must differ from browser/client/passkey hostnames. Its scheme/port/Host aliases cannot enter normal auth routes. Node's optional private bounded PEM mount enables native HTTPS without trusting forwarded headers; its listener now uses srvx's actual hostname option. Workers uses its canonical edge URL. Local workerd and certificate-verified Node/PostgreSQL transport checks are distinct from DNS/proxy/browser/deployment acceptance. Comment parents are covered using an explicit internal association fixture; this does not implement general comment attachment linking. Current clean-scan fixtures remain synthetic and 07.3f stays incomplete.

## Verified-unlinked cleanup refinement — 2026-10-04

A separate internal handler may reclaim supported finalized uploads only after an explicitly supplied retention-after-expiry interval, at least the capability grace. There is no destructive default or scheduler. Claims atomically require absence of every attachment reference and no live competing lease, mark policy deleted before external I/O and increment the intent revision. Form linking and scan transitions cannot accept that retired snapshot. Physical failure retains used bytes; resume claims preserve immutable identity. After owned-key deletion and absence checks, a fenced conditional transaction releases actual used bytes from project/global-principal counters exactly once, retaining finalized state and immutable metadata under deleted policy. The existing immutable-identity guard remains unchanged. Keys/metadata are retained as tombstones and can be swept again without another decrement. Existing expired-reservation cleanup cannot acquire a used-upload tombstone while its orphan lease is live. Linked content, unsupported legacy rows and tombstone compaction remain excluded pending separate explicit policy/verification. No schema, public route, audit, deployment or Module 09 scheduling is introduced.

The independent POSIX Node adapter admits one physical ClamAV process per instance, streams exact bounded input with no shell or inherited parent environment, limits output, applies process-group TERM/KILL and retains admission until child closure and private temporary cleanup. Explicit executable/verifier/certificate pins, independent official detached signatures, a read-only fixed three-database snapshot, freshness and pre/post asset fences bind the reported evidence. Matching per-file/PCRE limits to the unchanged 128-MiB aggregate budget passes supported 33-MiB and held 129-MiB/101-file archive cases. A fixed private service-binding capability plus independent bearer authentication transports exact streamed immutable bytes. Fresh request UUID, complete size/SHA-256 identity, a closed 2,048-byte reply and bounded deadlines prevent partial, replayed-to-another-request, mismatched or late outcomes from granting release. Node compares authentication before consuming input; no public callback, arbitrary endpoint, ambient outbound fetch, redirect or retry is introduced. Runtime startup still selects no scanner and default uploads remain unscanned/quarantined.

The workerd proof uses Miniflare's private native service callback to Node, with D1/R2 emulation; PostgreSQL 18.6 is real isolated local with S3 emulation. Neither historical key shape nor available aggregate quota proves those facts. ## Fixed S3 legacy recovery refinement — 2026-10-04

A separate internal provider capability is constructed for exactly one canonical retirement decision and fixed endpoint/bucket. Closed bounded ownership and accounting JSON manifests contain that exact historical snapshot; their original bytes must match the decision digests. Ownership binds endpoint, bucket, region, path-style addressing, reviewed multipart continuation mode and exact key; accounting binds the retained reserved/used/slot delta. A trusted operator must independently review these claims: constructing or hashing a manifest never proves ownership. No raw client or arbitrary-key delete operation is exposed. Ordinary BlobStore and current multipart validation remain unchanged.

This first S3 implementation requires a successful GetBucketVersioning response with absent Status/MFADelete before mutations and after absence checks; Enabled, Suspended, unknown or unsupported responses retain quota. R2 currently documents that operation as unsupported, so this adapter refuses it rather than interpreting 501/HEAD-null as absence. Provider-specific R2 recovery and versioned bucket recovery remain unfinished. Reject empty, dot and backslash path segments before I/O until exact historical address semantics are verified. Bounded prefix discovery preserves siblings, validates continuation, aborts only exact-key sessions, then deletes/HEAD-checks the exact object and repeats complete discovery under one 30-second cooperative deadline. Small HTTP responses are bounded before SDK XML deserialization. Released ledger keys remain for later sweeps; this does not establish quiescence or authorize compaction.


Pinned SeaweedFS 4.48 source and sanitized runtime experiments establish upload-ID ordering across mixed prefix keys, with NextUploadIdMarker-only continuation and no NextKeyMarker. The ownership manifest explicitly binds `multipartContinuation: "seaweedfs-4.48"` before this behavior is accepted; default `"s3"` mode refuses a mixed-key page without a key marker. Each next upload marker must occur in the returned page; all prefix rows/IDs count against the same bounds, duplicates/loops fail before object deletion, and only exact-key IDs are aborted. An observed undocumented empty R2 versioning response does not select this capability: known R2 endpoints are refused before I/O until a provider-specific contract is reviewed. The provider also checks actual wall-clock retention before I/O; callers still require the dual-store atomic retirement claim and lease-fenced release.


## Direct R2 historical absence refinement — 2026-10-04

R2-specific approved recovery uses its documented strong direct DELETE/read/list consistency, with no cached custom-domain path. The capability is bound to one canonical retirement decision and closed original ownership/accounting manifest bytes; ownership includes the fixed R2 account/bucket and explicit `r2-direct-delete-head-1` absence policy. All bytes/digests/snapshot/accounting and elapsed retention are validated before I/O. Header-signed direct list/abort/DELETE/HEAD requests use the existing R2 account destination and backend credentials, manual redirects, no-store and no automatic retries; exact historical key components are encoded and ambiguous path forms remain rejected.

Prefix discovery is bounded before mutations, siblings are preserved, exact-key sessions are aborted, direct object deletion must succeed and HEAD must be absent, then complete discovery repeats under one 30-second deadline and one active operation per capability. Retained ledger keys permit late re-sweeps. This establishes provider-visible object/session absence under the R2 contract, not internal physical byte erasure or inaccessible provider history. It does not interpret undocumented GetBucketVersioning responses, relax generic S3 refusal, infer ownership from inventory, fabricate current associations or select a public route/scheduler. Node and native workerd execution must verify the same owned-record proof on actual R2 before any scoped provider acceptance is claimed.
