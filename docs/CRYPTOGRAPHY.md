# Credential and recoverable-secret protection

Owner: [module 03](plan/modules/03-security-foundation.md). Direction: [ADR 0006](decisions/0006-credential-envelope-and-key-lifecycle.md) and the optional tier's [ADR 0007](decisions/0007-cloudflare-free-minimum-tier.md). The shared mechanisms, both key-source adapters and durable D1/PostgreSQL lifecycle/reference accounting are implemented and locally verified. The minimum-tier PBKDF2 mechanism exists, but its production parameter policy, startup pepper check, account integration and real Free-plan acceptance remain pending. The standard-profile Argon2id record service, both profile providers and login-time rehash are implemented and verified with the real providers on both standard profiles ([03.2e accepted 2026-09-29](plan/evidence/03-password-research.md)). Recovery and account linking remain module 04 scope.

TLS termination, platform hybrid key agreement, authentication distinctions and versioned capability evidence are documented in [TRANSPORT-SECURITY](TRANSPORT-SECURITY.md). Local capability is separate from deployed transport acceptance. Further audit work is [suspended by user instruction](plan/AUDIT-SUSPENSION.md); existing lifecycle audit writes remain intact.

## Credential format and digest

`generateOpaqueCredential()` returns `hb1_` plus the canonical unpadded base64url encoding of 32 bytes from `crypto.getRandomValues`. The prefix is public version metadata; all entropy comes from the CSPRNG. Never put the credential in a URL or persist it.

`digestCredential(provider, token, context)` stores `{v: 1, alg: HS256, key: {purpose: token-hmac, id, version}, digest}`. HMAC input is an unambiguous canonical tuple containing the HyperBug protocol namespace, algorithm/domain, context and token. `verifyCredential` uses platform `subtle.verify`, returning false for malformed credentials/records or invalid MACs and throwing a safe `CryptoFailure` for unavailable key/policy providers. Both outcomes must deny dependent authorization. No string comparison verifies a MAC.

The owning identity service must also bind the row to the account and purpose, enforce expiration/revocation, and atomically consume one-use credentials. A correct digest does not establish current permission. `migrateCredentialDigest` first verifies the old digest, then derives a current-key digest using a copied context; the caller updates storage under the appropriate revision/transaction. Previous nonrevoked key versions remain usable through the lifecycle policy, not an implicit fallback.

## Encrypted record

`encryptSecret` accepts 1–16384 bytes and a context with exactly `resourceType`, `resourceId`, `field`, `projectId` (UUID or null), and positive `schemaVersion`. Resource IDs are UUIDs; resource/field names are bounded lowercase slugs. Context must be constructed from trusted row/schema identity, not copied from unvalidated caller claims. It is authenticated additional data and need not be persisted a second time with the record.

Each call generates a fresh AES-256-GCM DEK and a CSPRNG 96-bit nonce. There is exactly one encryption per DEK. GCM uses a 128-bit tag. The DEK is wrapped by a purpose-specific AES-256-KW KEK. The self-describing record is:

```text
{
  v: 1,
  alg: A256GCM,
  wrap: A256KW,
  key: { purpose: envelope-kek, id, version },
  iv: canonical base64url of 12 bytes,
  wrappedKey: canonical base64url of 40 bytes,
  ciphertext: canonical base64url of ciphertext followed by the 16-byte tag
}
```

The context/AAD binds suite/version, resource, field, project and data schema version. Wrong context, IV, wrapper, ciphertext/tag, algorithm or key reference fails safely. Parsers reject extra fields, unknown versions, invalid/oversized encodings and wrong key purposes. Stored encrypted records never rely on an implicit current key.

`rewrapSecret` unwraps using the explicitly referenced retained key, authenticates the existing GCM payload/context, and wraps the same DEK with the current KEK. Ciphertext and IV remain unchanged. The temporary authenticated plaintext copy is zeroed and not returned/persisted. AAD deliberately excludes the mutable KEK reference so wrapper rotation does not re-encrypt data. The caller must atomically persist the new wrapper and update retained-key references; the `KeyRegistry` protected-record mutation supplies this atomic storage boundary.

Long-lived keys are imported nonextractable. A new/rewrapped DEK is temporarily extractable only because the standard wrapKey API requires it. No raw DEK leaves the service API. JavaScript string/GC behavior does not offer a guarantee that all historical memory copies are erased; these functions zero their owned byte buffers, avoid secret logs and do not claim hardware-backed isolation. Native plugins remain trusted code.

## Blind indexes and key separation

Token HMAC, blind-index HMAC, envelope KEK and minimum-tier password pepper use separate 256-bit material. The strict secret document rejects duplicate raw key material across any references using native HMAC verification; it also rejects duplicate IDs/versions within a purpose. HMAC payload namespaces additionally separate credential, blind-index and minimum-password protocols.

`blindIndexCandidates` accepts an already-normalized value of at most 2048 UTF-8 bytes and a context. The field owner defines normalization and must never persist a second plaintext copy merely to support lookup. Candidates include current and allowed previous versions, each tagged with its key reference. Lookup fan-out caps at three versions; a policy with more than three queryable blind-index versions fails instead of silently dropping an old index or issuing an unbounded query. Complete an index migration before exceeding that bound. Other retained envelope/token key reads may select from up to 32 key references.

## KeyProvider and authoritative lifecycle

`KeyProvider` exposes `current`, exact-reference `get`, and bounded `readable`. `SecretKeyProvider` loads its secret source and `KeyLifecycle.load(purpose, signal)` on every operation. It caches no credential or permission result. The lifecycle snapshot supplies a positive generation, authoritative current key, readable current/previous references, and all required retained-data/backup references. Current must be the first readable reference. Revoked references must be absent from readable even if their quarantined material still has to be retained.

All required/readable references must exist in the secret document. An omitted retained backup key blocks use rather than silently accepting an incomplete ring. Provider errors, malformed lifecycle state, absent keys and timeouts produce only `CryptoFailure`, without a path, provider payload or original cause. The source/lifecycle receive an AbortSignal; the default deadline is 1000 ms (allowed range 10–5000). Late source results cannot grant use after the deadline.

`createD1KeyRegistry` and `createPostgresKeyRegistry` implement the authoritative lifecycle. Every D1 read starts a new `first-primary` session and performs one snapshot query. PostgreSQL must use a primary pool. Current/previous versions are readable; revoked/removed versions are excluded. Snapshot and secret-source deadlines still fail closed. Do not substitute a dummy lifecycle or infer permission from material presence. Local workerd/D1 and PostgreSQL integration evidence does not prove live replication or provider backup compatibility.

## Secret source document and adapters

The secret source contains only `{v: 1, keys: [{ref: {purpose, id, version}, material}]}`. Material is canonical unpadded base64url of exactly 32 independently generated bytes. A document contains at most 32 entries and 16384 characters; the Node file additionally caps actual bytes at 16384. It is a secret, not an ordinary RuntimeConfig field. No example production key material is included here.

- **Workers:** The production root supplies `createWorkerKeyProvider(env.HYPERBUG_KEY_RING, createD1KeyRegistry(env.DB))` when D1 is bound. `HYPERBUG_KEY_RING` comes from a Worker Secret; `secrets.required` declares the name for local/staging/production and `pnpm types:cloudflare` generates binding types without reading live secrets. No beta Secrets Store is required. The binding factory and an actual Miniflare binding are tested; no live cloud secret/deployment was created.
- **Self-host:** The production root supplies `createNodeKeyProvider(HYPERBUG_KEY_FILE, createPostgresKeyRegistry(pool))` when the private file and a complete PostgreSQL transport are present. The separate abuse key file is optional for this provider; if present, both services share the bounded pool. The cryptographic file must be a POSIX regular file owned by the running UID with mode 0400 or 0600. Relative paths, symlink leaves, directories, loose permissions, wrong ownership, oversized/malformed files and cancellation fail closed. The source opens with O_NOFOLLOW/O_NONBLOCK, bounds the actual read despite file growth, checks metadata stability and closes the handle. Unsupported ownership semantics need another reviewed provider; they do not silently disable permission checks.

Both roots pass their provider into the shared server; without one, a route requesting a key receives a safe failure. Key material is loaded only for a dependent operation, so health-only startup without provider configuration remains possible. This root wiring is not account-route or deployed-provider acceptance.

For self-host rotation, prepare a complete private replacement file and atomically rename it into place; in-place mutation during a read is rejected when detected. Keep parent directories and filesystem ACLs restricted as part of deployment. Worker rotation preprovisions required material through the platform secret mechanism. Both profiles must coordinate authoritative lifecycle state and retained backups before removing any version. The health-only entry points do not yet instantiate a lifecycle-backed credential service; later composition must supply the real registry before identity routes.

No external cryptographic dependency was added. Workspace links connect both runtimes and database adapters to the infrastructure-free `@hyperbug/security` ports. The latest Workers type package was downloaded for reference, while installed dependency pins and compatibility date remain unchanged.

## Standard-profile Argon2id record and providers

`hashStandardPassword` and `verifyStandardPassword` implement the shared record and rehash contract for the two standard profiles. The exact v1 record stores `{v: 1, alg: Argon2id, memoryKiB, passes, parallelism, salt, verifier}` with canonical base64url of a fresh 16-byte CSPRNG salt and 32-byte verifier. It rejects unknown fields, formats and algorithms, including minimum-tier PBKDF2 records. Parameter validation enforces the source baseline of at least 19 MiB, two passes and one lane; memory is recorded in 1 KiB blocks and must be a multiple of four times the lane count so the stored value matches Argon2's effective allocation. Format bounds are at most 1 GiB, 32 passes and 16 lanes. These bounds are parsing safety limits, **not** approved deployment parameters.

Every caller must provide a deployment-selected current parameter set and maximum acceptable for stored records; there is no production default. Verification rejects a record above that maximum before costly provider work. The standard-profile maximum is a bounded functional policy; [ADR 0009](decisions/0009-standard-password-login.md) does not make further Argon2id performance characterization a login prerequisite. After a successful match, a lower parameter triggers a replacement with a new salt and the maximum of each old/current cost component; it never lowers a stronger component. The account owner must persist a replacement with an expected record revision after login. A true hash match alone does not establish an active account, valid session or permission.

The `Argon2idProvider` port keeps algorithm execution outside the shared record service. `createNodeArgon2idProvider` is the Node 24 provider using asynchronous `node:crypto.argon2('argon2id')` and native `timingSafeEqual` for fixed 32-byte comparisons. Its caller selects a 1–32-operation concurrency ceiling and an aggregate 19 MiB–4 GiB declared-memory budget; work exceeding either bound is denied without a queue. Password, salt, parameters and fixed-length verifier bytes are snapshotted before asynchronous derivation so caller mutation cannot change the comparison. Cancellation before or after derivation denies use, while an already started native derivation retains both reservations until the callback completes. The declared budget excludes native overhead; future deployment characterization may refine it without gating standard login under ADR 0009. Owned password/verifier/derived byte arrays are cleared where possible; JavaScript string and runtime copies cannot be guaranteed erased. The Node API is marked experimental in installed typings, and neither this functional check nor the archived probes establish audited provider coverage or production overload safety.

`createCloudflareArgon2idProvider` is the standard Workers provider based on pinned `libsodium-sumo` 0.8.4 and a separately imported, precompiled Wasm module. It uses the raw `crypto_pwhash` Argon2id13 and `crypto_verify_32` exports, initializes lazily inside a request because workerd forbids factory randomness in global scope, and retains one instance per isolate. The caller supplies a declared-memory ceiling; only one operation is admitted at a time, with no queue. The libsodium pwhash ABI does not expose parallelism, so this adapter explicitly refuses records with more than one lane rather than silently deriving a different hash. This local admission bound is not measured memory, CPU or overload evidence. The bundled package still contains its embedded Wasm image, but the factory hook supplies the separately imported module; paid Workers deployment and provider suitability remain open.

`createNodeStandardPasswordService` and `createCloudflareStandardPasswordService` bind an explicit standard-tier deployment selection and a snapshotted current/maximum record policy to their respective providers. Construction fails before account use if the tier is the Free minimum variant, if the Node verification maximum exceeds its declared memory reservation, or if the Workers maximum exceeds its declared memory ceiling or requests more than one lane. The shared `StandardPasswordService` exposes hash and verify with the accepted policy held immutably and returns the same revision-guarded replacement contract. Both production roots now select the initial source-minimum policy of 19 MiB, two passes and one lane for new and stored records, and supply the resulting service to the shared app. The Workers root constructs it only for the standard tier; the optional Free tier still refuses startup. The registration route now stores new Argon2id records atomically with User identity on both profiles, and the login operation verifies and transparently rehashes superseded records at their stored revision on both profiles.

The local Node and workerd functional tests match the same archived public vector at 19 MiB/two passes/one lane. The workerd test also checks correct and incorrect fixed-length verification and rejects unsupported parallelism. A Node-generated versioned record verifies in local workerd, and a local workerd-generated record verifies in Node. Wrangler 4.133.0 dry-run emits separate JavaScript and unchanged Wasm modules; their local Miniflare execution passes the public vector. The production-root dry-run also emits Wasm matching the pinned SHA-256 after the build copies the static asset. Shared unit tests cover strict records, algorithm separation, bounded stored costs, independent salts, non-downgrading rehash and fail-closed provider/cancellation behavior with a test provider. The new registration HTTP checks exercise one functional account write on each local profile. These are local functional and packaging checks, not paid Workers deployment evidence or a performance characterization. No new Argon2id performance test was run. Per [ADR 0009](decisions/0009-standard-password-login.md), independent audit is non-gating for standard-profile password login; further performance testing remains stopped and is not a gate. Recovery remains module 04 work, and the suspended Argon2id performance characterization (03.V5) stays open and non-gating. The optional Free tier continues to reject Argon2id records and stays disabled under its separate acceptance requirements.

## Optional minimum-tier password mechanism

`hashMinimumPassword` and `verifyMinimumPassword` implement only the PBKDF2-HMAC-SHA256 mechanism specified by [FREE-TIER-PROFILE](FREE-TIER-PROFILE.md). The caller supplies an accepted `currentIterations` and `maximumIterations` policy; the library has no production default or floor. The maximum bounds a stored record before pepper lookup or PBKDF2 work, so the parser's one-million-iteration format cap is never mistaken for an acceptable Free-plan cost. Invalid or reversed policy bounds fail closed. Each hash uses a fresh 16-byte CSPRNG salt, native Web Crypto PBKDF2 and a separate `password-pepper` KeyProvider HMAC key. Its strict record stores `{v: 1, alg: PBKDF2-HMAC-SHA256, iterations, key, salt, verifier}`. The MAC binds the derived bytes to the trusted account/field/schema context. Unknown fields, algorithms, key purposes and encodings fail closed. In particular, this verifier refuses Argon2id records; standard-profile hashes cannot be silently downgraded.

Verification uses native HMAC verification and returns a replacement record after a successful login when the active pepper changes or the accepted iteration count rises. It never reduces a record's iteration count: a previously stronger stored record can still verify when its count is within the configured maximum. A record above that maximum is denied before any provider call. The caller must atomically persist a replacement under the account's expected revision and authorize the account operation; a correct MAC alone is not a login. The integrated D1/PostgreSQL proof exercises protected-record revisions, pepper rotation, retained-backup pins, revocation and guarded key removal. Its 1,000/1,200-iteration values are functional fixtures, **not** proposed production parameters or performance evidence.

`createMinimumPasswordService` now snapshots one caller-supplied iteration policy and requires a current, correctly purposed password-pepper key before returning account-facing hash/verify operations. The startup check has a bounded wait and fails closed; each later operation still queries the provider so rotation or an outage cannot reuse the initial key silently. The service admits one operation per instance by default, with no queue; an explicit bounded concurrency ceiling may be selected by its caller. `createCloudflareMinimumPasswordService` additionally rejects the standard tier and retains the one-operation ceiling. These construction paths are not yet wired into the production root or an account route; their focused runtime tests are deferred.

The minimum tier still fails startup. Its separate plan requires 03.V7's measured cost on a real Cloudflare Free account and a reviewed parameter floor; production composition must invoke the pepper preflight before serving; module 04 must integrate the account and recovery journey; and independent tier acceptance must pass. ADR 0009 applies to the standard profiles and does not waive these minimum-tier requirements. No Argon2id performance test was run for this mechanism.

## Durable records, rotation and backups

Migration 0005 adds `key_registry_control`, `key_versions`, `protected_records`, `key_backups` and `key_backup_references`; 0006 improves indexed snapshot probes; 0008 widens the purpose constraint to `password-pepper` without changing those lifecycle rules. No raw keys enter these tables. Removed key identities remain permanent tombstones, with triggers preventing deletion/replacement, identity edits, illegal transitions or removal while referenced. Protected payload JSON must match its indexed key reference. Fresh/previous-schema upgrades are tested independently on both profiles.

The internal `KeyRegistry` capability is available only to trusted composition and maintenance code. It is not an HTTP route, plugin capability or grant to project administrators. `mutate` requires an expected global generation, fresh audit/request UUIDs and trusted server time. D1 CHECK guards make stale or zero-row preconditions abort the whole batch. PostgreSQL serializes through that same generation row within a transaction with one-second statement/lock limits. No external crypto, file or network work happens inside the transaction. Conflicts do not retry automatically; after an ambiguous outcome inspect authoritative state and the audit ID before taking another action.

A protected-record `put` stores a strict digest/envelope/minimum-password record and key reference together, with expected revision zero for create or the current positive revision for replacement. New writes must use the currently active key, so a rotation between computation and persistence rejects a stale write. Successful rewrap/digest/password/index migration updates payload and reference atomically; a failed audit insert rolls both back. Deletion requires the expected revision. Future owners must bind record IDs to their authorized account/project/resource and use new UUIDs for new records; this primitive is not a public generic secret store or an identity transaction implementation.

Rotation procedure:

1. Preprovision independent material under a never-used reference in the complete secret source, retaining every readable/required version.
2. Activate the new reference with the observed registry generation. The old current becomes previous. There are at most 32 nonremoved versions overall and three readable blind-index versions; migrate/remove eligible versions before exceeding either bound.
3. Rewrap envelopes or recompute credential/blind-index digests through the shared services, then persist each result using its expected record revision. There is no plaintext re-encryption or implicit fallback.
4. Keep old material while any data or backup references it. Once references are gone, `remove` writes a tombstone; only then may an operator remove the corresponding physical material. At ring capacity, remove an eligible old reference/material before preprovisioning another.
5. For compromise, revoke immediately. Revocation remains available during backup capture and may intentionally leave a purpose without a current key. It never releases data/backup pins or destroys recovery material.

`begin-backup` pins every nonremoved key before capture starts. One capture may be open at a time; activation/removal is denied during it. `finish-backup` retains all pins. Expiry alone does nothing: `release-backup` also requires the trusted operator's `destroyed: true` attestation that **every copy** is gone. A failed capture remains pinned through the same explicit cleanup path. These methods coordinate lifecycle accounting; they do not create, inspect or destroy provider backups. Module 13 must implement and verify that orchestration and reconcile all retained manifests and later revocations **before** enabling a restored database. Restoring an old registry alone must never authorize old revoked material.

Every successful mutation appends one sanitized `core.key-registry` audit event in the same transaction. Audit contains action, safe target, request and generation, without payloads, digests, raw material or free-form error details. Failed transactions return a fixed `KeyRegistryFailure`; permission-aware audit access and failed-action diagnostics remain 03.3 work. The global generation is bounded to 2,147,483,647 and fails closed at exhaustion; do not reset it or replay old intents. A reviewed widening migration is required before exhaustion. The global mutation lock favors consistency and is a throughput constraint to account for in module 04/10 load tests; snapshot reads do not take it.
