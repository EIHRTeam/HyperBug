# Issue Forms and Markdown templates

Module 07 owns this format. The current implementation provides YAML decoding, canonical schema validation, immutable form/template versions, authorized management/read APIs and atomic issue submission with retained structured answers. Attachment-bearing submissions atomically consume only matching released, current-clean-scan uploads; actual scanner acceptance and isolated download delivery remain separate Module 07 work. Audit behavior in 07.2e remains suspended. Local evidence is recorded in the Module 07 progress and validation files; no provider/deployment acceptance is implied.

## Authoring and compatibility

Definitions accept one GitHub Issue Forms YAML document or the normalized version-1 JSON shape. YAML is an authoring format, not persisted source. There is no byte-for-byte round trip, GitHub API/repository synchronization, repository discovery, chooser `config.yml`, Markdown-template front matter, or standalone Boolean field. Unknown keys and unsupported attributes fail explicitly rather than being ignored.

| Surface | Supported behavior | Bounds and deliberate deviations |
| --- | --- | --- |
| Top level | Required `name`, `description`, `body`; optional `title`, `labels`, `assignees`, `type` | Name 100, description 500, title 200 Unicode scalar values. Labels/assignees accept arrays or comma-separated names, at most 32 distinct names of 100 scalars. `type` is a project issue-type name. These are authored defaults, never authority or resolved project IDs. `projects` is rejected: GitHub project-board assignment is outside Core. |
| Elements | `markdown`, `input`, `textarea`, `dropdown`, `checkboxes`, `upload`; `attributes`, applicable `validations`, optional `id` | 1–64 elements with at least one answer field; no nested/group fields. IDs are distinct ASCII letters/digits/underscore/hyphen, 1–80 characters; reserved prototype names rejected. Missing IDs become `field-1`, `field-2`, etc. in body order, including notices. Authors should provide IDs to keep editor identity stable; positional IDs are scoped to the immutable form version. |
| `markdown` | `attributes.value`; display-only and never submitted/generated | At most 8,192 scalars. Validation keys unsupported. Notices must use the central content policy when exposed to a rendered consumer. |
| `input` | `label`, `description`, `placeholder`, `value`; validations `required`, `min_length` | Single-line answer/default/placeholder, at most 1,024 scalars; min_length 0–1,024. |
| `textarea` | Same attributes/validations as input; optional `render` | Multiline answer/default/placeholder, at most 16,384 scalars; min_length 0–16,384. `render` is a safe code-fence language token of 1–32 letters/digits/underscore/plus/hyphen; no dependency on the GitHub Linguist language registry. File links in Markdown remain subject to the attachment delivery policy. |
| `dropdown` | `label`, `description`, `options`, `multiple`, integer-index `default`; `required` | 1–64 distinct nonempty options, each at most 200 scalars. Default index must exist; defaults with `None`/`n/a` options are rejected, case-insensitively. Single choice is a string; multiple choice is an array of exact option strings. Duplicate/unknown selections rejected. |
| `checkboxes` | `label`, Markdown `description`, `options` with Markdown `label` and per-option `required`; group `required` | 1–64 distinct labels, at most 200 scalars each. Answers are arrays of zero-based option indices. Each required option must be selected; required group means at least one choice. No implicit checkbox consent/default. |
| `upload` | `label`, `description`; validations `required`, `accept` | `accept` is a comma-separated list of at most 32 extensions (`.png`, `.tar.gz`, etc.), normalized to lowercase. MIME wildcards are rejected. Answers are distinct opaque attachment UUIDs, at most 16 per field and 32 per submission. Extension hints do not grant upload permission or override Core size/type/quota/scan policy. GitHub's advertised 10/25/100 MB limits are not HyperBug acceptance limits. |

All answer-field labels are nonblank single-line strings of at most 200 scalars; descriptions are at most 2,048 scalars. Booleans must be booleans, indices/minimum lengths must be bounded nonnegative integers. Scalar strings must be valid Unicode without NUL or other non-text control characters; tab, LF and CR are allowed only in multiline text. Required answers reject whitespace-only text. Optional empty text is allowed; a nonempty answer still meets min_length. Validation applies equally to public and private projects.

## YAML and canonical JSON boundaries

`yaml@2.9.1` uses YAML 1.2 core schema, strict syntax and `uniqueKeys: true`. The decoder rejects all errors/warnings, additional documents, directives, explicit tags (including core tags), anchors/aliases, merge keys, non-string/complex mapping keys, prototype keys and non-finite scalars before JavaScript conversion. YAML comments, quoted scalars, folded/literal blocks, flow arrays/maps and ordinary YAML 1.2 booleans/integers are supported. Quote strings that would otherwise resolve to booleans or numbers.

The source is limited to 32,768 scalar values and 65,536 UTF-8 bytes. Before parsing, lexing limits flow depth to 12 and tokens to 32,768; conservative indentation (48 spaces) and inline block-sequence depth (12) limits also apply to scalar content. Before conversion the AST is limited to depth 12 and 8,192 nodes; aliases are never expanded (`maxAliasCount: 0` provides an additional guard). There are no custom tag constructors. Errors expose a stable reason without echoing source text.

Canonical JSON uses `schemaVersion: 1`, the supported top-level keys and the supported element shape. Normalization supplies explicit empty defaults, required flags and minimum lengths, and stable IDs. Canonical validation rejects unknown versions/keys, non-JSON objects, accessors, cyclic/shared graphs, sparse arrays and prototype keys. The resulting definition must remain within 65,536 serialized UTF-8 bytes and 65,536 stored scalar characters on both dialects. The portable character bound includes the spaces PostgreSQL `jsonb::text` adds after object colons and array/object commas outside strings; escaped quotes, backslashes and separators inside strings remain data. Canonical schemas and answers contain no floating-point numbers. This rejects a definition before one profile can store a value the other profile cannot. API transport byte/string/node limits still apply independently and may be smaller than the format ceiling. Parser dependencies are isolated behind `@hyperbug/security/issue-form-yaml`; application/domain and auth/ingress roots do not load YAML parsing.

## Submission and version invariants

Submission carries the form ID, exact immutable version and values, plus an optional `draftId` that is required when upload answers are nonempty. The active version must match and the form must be enabled; changed/disabled forms produce `FORM_VERSION_STALE` and the caller reloads the definition. Drafts are version-pinned: there is no automatic remapping based on IDs, option text or body position. Client editing/prefill does not supply server authorization, and omitted fields do not silently adopt authored defaults at submission.

The atomic issue-creation operation repeats the active-version/principal/project/reference checks and persists the canonical structured answers with the form version alongside the issue, timeline, outbox and receipt. Updating the issue body later must preserve the original structured submission/version as provenance. New definition versions must not mutate old versions. Markdown templates retain immutable snapshots behind every revision, including enable/disable changes.

The pure validator verifies answer shape and syntax only. Persistence atomically reauthorizes each referenced upload against the submitting principal and project, matching `issue-draft`/`draftId`, finalized immutable identity, used quota, released `ready` state, no processing lease and the current completed clean scan policy/result. Every upload field enforces its extension allowlist against the stored normalized filename; this does not establish safe content. Missing/wrong draft, foreign owner/project, pending/unscanned/quarantined/infected/failed/stale-policy files and previously consumed IDs fail with `FORM_ATTACHMENTS_INVALID`, without partial issue, attachment, provenance, number, event, outbox or receipt changes. Empty optional upload answers remain valid. Required upload fields can be submitted only with valid released uploads. The current tests use explicitly synthetic trusted scan results; no actual scanner or malware detection is claimed.

Generation follows schema order, never answer-object key order. Multi-select and checkbox selections follow option order; attachment IDs sort lexically. Newlines normalize to LF. Notices/descriptions/placeholders are excluded; text defaults are not silently submitted. Plain headings/selected dropdown labels are escaped, textarea Markdown remains canonical author text, and `render` uses a fence longer than every backtick run in the answer. Checkbox labels retain authored Markdown. Attachments become opaque `/attachments/{id}` links, with no signed URL or filename in generated Markdown. All generated content must pass the central final sanitizer/projection before issue creation; the result is limited to 32,768 scalars / 131,072 bytes including headings and fences.

## Management, reads and submissions

All paths begin `/api/v1/projects/:projectId`. IDs are opaque UUIDs; definitions and submissions never cross projects.

| Path / method | Input or result | Authorization |
| --- | --- | --- |
| `GET /forms`, `GET /templates` | `{ items: [...] }`, bounded summaries only; optional `includeDisabled=true` | Enabled current summaries follow project visibility; disabled heads require `content:history` |
| `GET /forms/:id`, `GET /templates/:id` | Current detail; optional `version` pins an immutable snapshot | Enabled current detail follows project visibility; pinned or disabled detail requires `content:history` |
| `POST /forms` | `{ format: "yaml", source, enabled }` or `{ format: "canonical", definition, enabled }`; 201 detail | `content:manage`, maintainer or administrator |
| `PUT /forms/:id` | Same complete desired state plus `expectedRevision` | `content:manage`; optimistic revision check |
| `POST /templates`, `PUT /templates/:id` | `{ name, body, enabled }`; replacement additionally requires `expectedRevision` | `content:manage`; 201 on create, revision check on replacement |
| `POST /forms/:id/submissions` | `{ formVersion, values, title?, draftId? }`; 201 Issue document | `issue:create`, same principal/project admission as ordinary issue creation |

A `.yml` authoring file is submitted as its string contents in `source`; there is no definition-file upload endpoint. The combined form/template catalog is capped at 64 heads per project, including disabled heads. Names are exact and case-sensitive across both kinds. Every successful save appends the next snapshot and advances the head; no version/head deletion endpoint exists. A pinned detail reports its selected content/version and the **current** head `revision`/`enabled`, so callers do not confuse historical content with the current draft submission target. Template legacy snapshots use `createdAt: null` when their original creation time is unknown. Lists do not return schemas, bodies or derived trees. Details expose canonical editor data alongside centrally sanitized trees (`renderedFields` for Markdown notices/descriptions/checkbox option labels, `bodyTree` for templates), the content policy and an ETag including selected version and head revision. Every response is no-store.

Both content permissions require a current maintainer-or-higher Staff membership. `content:history` is a read permission, so authorized history remains available on an archived project; `content:manage` denies archived writes. Private projects remain invisible to nonmembers. Disabled current detail is hidden from other callers. The API has no audit side effect under the current suspension.

An omitted submission title uses the pinned form's authored `title`; the resulting title still must satisfy Issue policy. Blank/missing titles without a valid authored title fail. Authored field values remain editor prefills, never silently submitted answers. Authored label/type names resolve through the project's existing normalized taxonomy keys; assignees resolve exact local HyperBug account handles to **active Staff project members**, never display names, emails or GitHub accounts. Unknown, ambiguous, duplicate or out-of-policy defaults fail clearly. These APIs do not accept arbitrary taxonomy overrides on form submissions. The issue limit of 20 labels / 10 assignees applies even though the definition format permits 32 authored names.

The shared repository checks a successful receipt **before** active form/default resolution, so a committed same-key/same-payload request remains replayable after disable/version/default changes. Current API authentication/authorization still applies. A fresh stale draft fails `FORM_VERSION_STALE`; the server does not remap answers. The repository regenerates Markdown and rejects a direct port caller's mismatched body. PostgreSQL locks the project before receipt FK insertion and the form/default rows; D1 repeats the form/principal/default predicates inside its batch and forces rollback with a NOT NULL witness if a precondition loses a race. Neither failure consumes an issue number or leaves partial issue/answer/event/receipt rows. Up to 32 attachments are consumed in this same operation, each retaining its upload intent ID as the attachment ID and its immutable final key, canonical SHA-256 version/digest, type and actual bytes. Consumption promotes the upload association from draft to the created issue and increments the upload revision, so later processing inherits current parent authorization. Quota remains used. PostgreSQL locks intent/detail/result rows beneath its project-first transaction; D1 uses per-file scalar NOT NULL witnesses that repeat current ownership, draft, revision, readiness and scan identity/policy/evidence checks. A zero-row guard or unique consumption conflict rolls back the complete batch. An identical concurrent winner is checked again before returning changed-attachment errors; receipt replay still precedes form/version/attachment checks.

D1 migration `0019_template_versions` / PostgreSQL `0018_template_versions` adds template snapshots, seeds only each legacy head's currently known revision, and protects template versions and submissions from mutation. Unknown legacy time uses an internal zero sentinel exposed as null. Older revisions are not fabricated; legacy noncanonical form definitions are not silently rewritten. Recovery retains these additive tables and immutable history during application rollback, with a reviewed forward fix for malformed legacy content. No remote migration has been applied.
