# Rate limiting and abuse controls

Owner: [03.3c–03.3d](plan/modules/03-security-foundation.md). Decision: [ADR 0008](decisions/0008-rate-limit-consistency.md). Status as of 2026-09-27: shared counters and adapters have local evidence, and registration is the first owned route; deployed consistency and 03.V3 acceptance are open. Audit work is [suspended](plan/AUDIT-SUSPENSION.md).

## Classes and dimensions

Core has ten rate categories: login, password reset, registration, Issue creation, comment creation, reaction, search, attachment upload, API-token creation and webhook configuration. Categories are route classes, not a raw URL supplied by a caller. Each owning route must select relevant IP, account, principal, project, token and route dimensions; it must not rely on one global IP key. CAPTCHA success does not skip any limit.

The shared admission policy requires these minimum independent dimensions before it reads an abuse key or writes a counter. A route may add another dimension or window within the existing write cap; it cannot substitute one for a required dimension.

| Categories | Required dimensions |
| --- | --- |
| Login, password reset, registration | Account and trusted client IP |
| Issue creation, comment creation, reaction, attachment upload, webhook configuration | Authenticated principal and target project |
| Search | Trusted client IP and stable route class |
| API-token creation | Authenticated principal and trusted client IP |

This matrix sets no numerical budget. Account canonicalization belongs to the identity route; principal/project IDs must come from authenticated and authorized server state, and the route class must be a server constant. Any category requiring an IP remains unavailable when its deployment cannot establish trusted client-address provenance. An authenticated or CAPTCHA-verified result does not waive the matrix.

The approximate `VolumetricLimiter` port is only an early load-shedding layer. The Node adapter keeps bounded process-local buckets and denies on capacity exhaustion or invalid keys. The Workers adapter uses the platform Rate Limiting binding, whose counters are local to a Cloudflare location and eventually consistent. These are never the sole login, recovery or privileged-operation gate. `wrangler.jsonc` declares `ABUSE_VOLUMETRIC` separately for local, staging and production, each with a distinct namespace and a provisional 1,000-call/60-second ceiling. The configured Node sensitive-admission root now uses the same provisional per-digest limit with a 10,000-key process cap. Generated Env types and a Miniflare/workerd binding exercise pass. Deployment, location-scope and provider-outage behavior remain unverified; the provisional ceiling is not a measured category policy.

The sensitive `RateCounterStore` is backed by migration `0007_rate_limits` in both D1 and PostgreSQL. It stores one row per `(category, dimension, key version, subject digest, window start)`. The primary key isolates attempts; an indexed expiry supports bounded cleanup. D1 and PostgreSQL each execute one atomic upsert that increments and returns the count. The D1 statement is a write routed to the primary, avoiding a stale replica read; PostgreSQL serializes conflicting row updates. The count saturates at signed 32-bit maximum and is never reset inside its window. A second window creates a separate row.

`checkSensitiveRateLimit` validates the rule and row, consumes an attempt, then returns remaining capacity or a whole-second retry hint. It returns `unavailable` on invalid policy, corrupt output or storage failure; callers must deny, not fall through to the protected action. The shared HTTP boundary has closed `RATE_LIMITED` (429) and `RATE_LIMIT_UNAVAILABLE` (503) errors, with a bounded `Retry-After` header only for limited responses. `requireSensitiveRateAdmission` is the shared route-facing bridge: it runs the authoritative key/counter admission within an explicit 10–5,000 ms route-selected deadline, returns only on an allowed and still-active request, and otherwise throws the safe 429 or 503 before the caller's side effect. Missing or invalid deadlines, a stalled key source or counter, a malformed limited hint, and unexpected provider failure map to 503. The deadline aborts the admission signal and denies promptly even when a provider ignores cancellation; an already-dispatched counter write may still finish later, but no protected action follows the timeout. The registration route now supplies canonical account and root-trusted IP subjects, provisional budgets and a 1,000 ms admission deadline. Other route owners must do the same with their own measured rules and avoid revealing whether an account exists.

The shared app also decorates `sensitiveAdmission` with a guard bound to its optional CAPTCHA gate and root-selected abuse-key, approximate limiter and primary counter sources. A route cannot substitute those sources through its admission intent; missing authoritative dependencies deny with 503. The Cloudflare root binds its D1 rate store, Worker Secret source and `ABUSE_VOLUMETRIC` binding when D1 exists. The Node root binds its PostgreSQL store, separate private abuse-key file and bounded local limiter when configured; partial setup refuses startup, while no setup leaves sensitive admission closed. The bound guard replaces every route-supplied IP subject with the root's trusted client-address result before admission. Node uses its native socket peer; the Cloudflare root verifies a short-lived signed assertion when its ingress secret is configured and otherwise denies IP-required categories before counter writes. Local multiworker registration passes; deployed gateway provenance and private routing remain pending. Other dimensions remain the route owner's responsibility. The admission snapshots one active key ring, derives versioned HMAC subjects, consumes one approximate slot for the current key of each distinct dimension, then uses the primary store across every active key version. An approximate limit denies with 429 and no invented retry hint; malformed or unavailable approximate service denies with 503. An approximate allowance never skips the primary counter. CAPTCHA verification follows only after both layers allow. A rate denial avoids a provider call; a failed or unavailable configured challenge denies after consuming the rate attempt. With no provider, the same route admission succeeds without a token after the independent rate check. The registration route now uses this composition before Argon2id hashing and atomic account writes. Local Node/PostgreSQL and workerd/D1 route tests exercise actual primary counters and active key versions; a local multiworker test also exercises the production Workers root through the signed service-bound ingress. Deployment acceptance remains open. The current account budget of 5 attempts per handle and IP budget of 20 attempts per 60 minutes are provisional, not measured deployment policy.

Both production roots now make `/health/ready` depend on a parseable abuse key ring and one read-only schema query over the primary-counter and registration credential tables; Workers also requires the approximate binding to be present. No configuration, an unreachable Node pool, or a missing table returns `unavailable` without exposing provider detail. This probe does not write a counter/account, prove write permission, establish a trusted Workers IP, or substitute for multi-instance/outage acceptance. Liveness remains independent of those dependencies.

`checkSensitiveRateLimitVersions` consumes every active HMAC key version for one category and dimension before deciding. A limit on an old version still denies while the new version accumulates the same attempts; failure of any version denies. It rejects empty, duplicate-version, mixed-category or mixed-dimension inputs before writing. Route composition must supply all active versions from its approved key source and retain the previous version for at least the longest configured rate window. This does not replace the pending key-source integration or prove that rotation is scheduled correctly.

`checkSensitiveRateLimits` composes a route's sensitive checks. It requires the category's mandatory dimensions, at least two distinct dimensions, the same active key versions in each check, no duplicate dimension/window pair, and at most 16 counter writes across at most eight checks. It validates the complete policy before writing, then consumes every dimension/window/version even when another check is limited. Any unavailable counter denies the whole operation; limited responses carry the longest applicable retry hint. Route owners still choose and measure category thresholds and supply trusted canonical subjects; the helper cannot infer those from an HTTP request.

`checkSensitiveRateAdmission` joins the key provider to this counter policy. It validates a route's category, mandatory dimensions, bounded rules, distinct dimensions and canonical IP syntax before reading secrets; snapshots the supplied subjects and rules before any await; reads the active abuse-key ring once; derives every selected dimension/window from that same version set; then applies optional approximate checks and the authoritative counters. Missing, malformed, cancelled or failed key/counter operations return `unavailable`. It does not derive identity from a request, authenticate a caller, decide an endpoint's budgets, or make the approximate limiter authoritative. The route owner must pass trusted canonical non-IP subjects and deny every non-allowed decision before its side effect.

The detailed admission variant returns versioned subject digests only after all rate checks allow the attempt; denied decisions expose no digest set. The minimum-tier login service consumes that one snapshot for D1 account lockout and its later failure/success transition, avoiding a second key-ring read between rate admission and lockout. It still needs a route-selected canonical account/IP and measured budgets before any product login can use it.

The server guard is verified through an HTTP fixture in both runtimes: two successful calls run a protected action, the third is 429 with a bounded retry hint, and key outage, counter outage, noncooperative key/counter stalls or invalid policy/deadline return 503 with no additional action. The fixture uses an in-memory counter to prove the route ordering and response mapping; the separate repository contract proves D1/PostgreSQL counter behavior. This is not a production login or an end-to-end multi-instance deployment test. The real route owner must still compose a trusted address/account source, an actual primary store and measured budgets.

## Privacy, retention and integration

`abuseSubjectDigest` requires a dedicated non-extractable 256-bit HMAC-SHA256 signing key. It domain-separates category and dimension, and returns a lowercase digest plus key version. A trusted caller must canonicalize the subject first: IP from a verified proxy boundary, account identifier in the same canonical form used by identity lookup, current principal/project IDs, or a token fingerprint. Do not hash an attacker-controlled `X-Forwarded-For` value or store the raw input in the counter.

`canonicalIpAddress` rejects hostnames, forwarded chains, ports, IPv6 zone identifiers, ambiguous IPv4 forms and unspecified addresses; it normalizes IPv6 and IPv4-mapped IPv6 consistently in Node and workerd. This only verifies address syntax. The Node adapter's `nodeSocketClientAddress` reads `srvx`'s native socket peer through `request.runtime.node.req`, ignoring all forwarding headers; an actual loopback HTTP test with forged headers proves that path. Behind a reverse proxy, the peer is the proxy, so per-client IP enforcement needs a separately verified proxy trust model. The Workers profile now has a local functional signed-ingress path: a controlled public gateway signs the direct-edge address for a private service-bound API Worker. A missing or invalid assertion denies before counters. Cloudflare documents that a same-zone Worker subrequest can influence `CF-Connecting-IP` through mutable `x-real-ip`, so the public gateway's zone exclusivity and subrequest rejection require deployed adversarial verification before its IP provenance is accepted. See [ingress evidence](plan/evidence/03-workers-ingress.md). Missing trusted provenance must deny any route that requires the IP dimension.

The dedicated abuse secret is a strict JSON document in a Worker Secret named `HYPERBUG_ABUSE_KEY_RING` or a separate Node private-file mount. Its shape is `{ "v": 1, "current": 2, "keys": [{ "version": 2, "material": "base64url-32-byte-key" }, { "version": 1, "material": "base64url-32-byte-key" }] }`: current first, then decreasing active versions, up to eight distinct versions/materials. The parser imports each as a non-extractable sign-only HMAC key, zeroes decoded bytes and denies malformed, missing, cancelled or timed-out sources. `activeAbuseSubjects` derives every active digest for one trusted canonical subject, while the route-facing admission function snapshots one ring for all checks. Generate actual material with a CSPRNG, never reuse the credential/envelope ring, and retain the previous version through the longest live rate window. Both roots compose registration and login with the primary store; deployed real-secret provisioning and cross-location behavior remain open.

Rows expire after the window closes plus a bounded retention interval. A later increment may shorten an existing row's expiry but never extend it. `purgeExpired` deletes at most 1,000 eligible rows per call through the expiry index. The Node root schedules a non-overlapping batch every five minutes and stops it before closing its PostgreSQL pool. The Workers root declares the same five-minute Cron in each environment and runs one D1 batch per invocation. A failed batch is retried by the next invocation; neither runtime drains an unlimited backlog in one call. Local timer and workerd scheduled-handler tests pass. A temporary one-minute Cron against isolated `hyperbug-test-1` also purged an expired row while retaining a fresh row; tracked five-minute deployment and physical retention under sustained load remain unverified. Module 09 still owns the broader retention jobs. The configured abuse-metadata retention remains separate from security logs, credentials and existing audit records.

## Verification and remaining acceptance

Local tests on 2026-09-25 cover 20 concurrent increments against each actual profile adapter, independent dimensions/windows, fail-closed storage behavior, bounded purge and malformed digests. D1 ran in workerd/Miniflare and PostgreSQL ran in an isolated 18.6 cluster. Unit tests cover HMAC domain separation and rejected extractable keys; source tests cover private Node files and a workerd Worker Secret binding. The local Miniflare rate-limit binding permits two calls and denies the third. Typechecks, lint and migration history checks pass. This is local/emulated evidence, not a deployed multi-location claim.

The 2026-09-26 local consistency extension uses two distinct PostgreSQL connection pools against the same private 18.6 database and two named Miniflare Workers bound to one local D1 identifier. Six concurrent attempts alternate between each pair; exactly three are admitted at a three-attempt limit, and the successful decisions report remaining capacity 2, 1 and 0. Closing one PostgreSQL pool makes its next check `unavailable`, while the surviving pool can admit an attempt in the next window. The D1 test uses separate Worker entrypoint instances but does not model a deployed account's geographic locations, replica routing, provider outage or ingress trust. Both checks strengthen the local primary-counter consistency evidence while 03.V3 remains open.

The account login route now has focused local evidence on both standard profiles that a previous active HMAC-key version at its account limit still denies after the current-version approximate bucket allows. Both primary stores record the denied attempt against the previous and current key versions. This protects the limit during key overlap, but deployed rotation timing and old-key retirement remain unverified.

Before checking 03.3c–03.3d or 03.V3 complete, extend the real-route use beyond registration/login to the appropriate recovery, principal, token, project and privileged categories as their owning routes arrive; provision distinct real secrets; verify namespace IDs in the account; prove genuine trusted client-address extraction; measure budgets and physical retention; and test multiple independent instances, locations and outages. Registration/login already use account plus trusted-IP dimensions with primary counters on both local profiles. The minimum tier additionally needs D1 account lockout/progressive delay, required CAPTCHA when configured and alerting under 03.3h; this document does not enable it.

The optional minimum tier now has a separate D1 failure-streak store and bounded progressive-delay policy under migration `0009_account_lockouts`. They are not used by a production route and do not replace the primary rate counters or establish trusted Workers ingress. The account route must use the same canonical account subject for all active HMAC key versions, deny on any store failure, and avoid leaking account existence. A D1 read-replication change would require a new consistency decision before this store can admit login attempts.

The shared server now exposes deadline-bounded lockout admission, failed-password recording and verified-success clearing. Admission returns only on an unlocked and still-active request; a lock returns the existing 429 code and bounded retry hint. Missing, malformed, stalled or failed D1 state returns the existing 503 code. A late D1 write after a timeout cannot turn a denied login into success. These guards are available to the future account owner but are not wired to a product route or production composition root.

`createMinimumLoginAdmission` composes authoritative login rate admission, lockout and optional CAPTCHA in that order, then returns a one-use permit for exactly one failure or verified-success transition. A rate denial avoids D1 lockout and CAPTCHA work; lockout denial avoids CAPTCHA work. Complete CAPTCHA bindings require verification by default, while no provider still requires both rate and lockout admission. This service is not constructed by either production root while the tier is startup-disabled.

A 2026-09-26 Context7 resolve-then-query follow-up selected the high-reputation Cloudflare Workers documentation `/llmstxt/developers_cloudflare_workers_llms-full_txt` for incoming address provenance. Its [HTTP header reference](https://developers.cloudflare.com/fundamentals/reference/http-headers/) says direct requests have the client's `CF-Connecting-IP` and a stripped `x-real-ip`, while same-zone Worker subrequests derive `CF-Connecting-IP` from `x-real-ip`, which Worker code can alter. The retrieved material did not establish a trusted same-zone discriminator for this deployment. Therefore the current code does not add a `CF-Connecting-IP`-only sensitive-rate adapter. Before accepting an IP dimension on the Workers profile, verify a deployment ingress policy that excludes or authenticates same-zone subrequests and test that policy on the target account. Cross-zone subrequests use a fixed Worker client IP and also cannot establish the original caller's address for this purpose.

A 2026-09-27 Context7 resolve-then-query follow-up reconfirmed that Cloudflare's [request properties](https://developers.cloudflare.com/workers/runtime-apis/request) do not document a direct-client/same-zone discriminator and that its [header reference](https://developers.cloudflare.com/fundamentals/reference/http-headers/) retains the mutable same-zone `x-real-ip` behavior. The ingress gap therefore remains open. Context7 also documented a [D1 `SELECT 1` binding probe](https://developers.cloudflare.com/d1/llms-full.txt) and [node-postgres `Pool.query`](https://github.com/brianc/node-postgres/blob/master/docs/pages/features/pooling.mdx); the deployed profile probes remain unverified despite local tests.

The 2026-09-26 Node root composition used Context7 resolve-then-query for [node-postgres pooling](https://github.com/brianc/node-postgres/blob/master/docs/pages/apis/pool.mdx), [TLS configuration](https://github.com/brianc/node-postgres/blob/master/docs/pages/features/ssl.mdx) and [Unix-socket connection options](https://github.com/brianc/node-postgres/blob/master/docs/pages/features/connecting.mdx). Pool construction is lazy, `pool.end()` drains clients, and an idle-client error listener is required. The TCP URI rejects query parameters because the driver can overwrite an explicit SSL object when SSL URI options are present. TCP outside local loopback uses certificate verification; an explicitly configured absolute Unix-socket directory avoids a network segment. The root has bounded connection/query settings. A local isolated PostgreSQL 18.6 test now loads the private abuse key through this root and gets an allowed first account/IP attempt followed by a limited second attempt through its socket-backed primary store. The bound IP source uses the already-proven srvx native socket path; no additional library lookup was needed for that internal composition. This is functional local evidence, not a deployed PostgreSQL session, verified reverse-proxy provenance or route acceptance.
