# Outbound request security boundary

Owner: [03.3e](plan/modules/03-security-foundation.md). Status: shared mechanism implemented; runtime-specific egress validation and integration remain open. This policy applies to provider and plugin HTTP calls that Core initiates. It does not authorize arbitrary destination URLs.

## Current mechanism

`createOutboundFetcher` in `packages/security/src/outbound.ts` accepts a trusted catalog of HTTPS origins and exact method/request-target pairs and requires an explicit transport. A caller chooses a catalog ID and supplies only a declared relative target. Each destination must declare one to 32 distinct GET or POST operations; an operation's optional query string is fixed as part of the exact target. Policy construction rejects a missing transport, malformed/noncanonical origins, URL credentials, IP literals, private-looking hostnames, duplicate or malformed operations and unbounded limits. Each request rejects unlisted path/method/query combinations, scheme-relative and absolute paths, fragments, control characters, backslashes, encoded pathnames, noncanonical relative targets, unapproved headers, oversize bodies, and absent destinations before network dispatch. The wrapper snapshots the reviewed catalog at construction so later caller mutation cannot expand it.

The wrapper sets `redirect: 'manual'` and `cache: 'no-store'` and accepts only 2xx responses. It never follows a provider-supplied `Location`; a change of host would need a separate reviewed catalog entry. On the Cloudflare profile, the explicit `cache_option_enabled` compatibility flag supports the no-store subrequest option so credential-bearing provider responses do not use the normal Workers fetch cache path. The Node direct HTTPS transport does not use a shared HTTP cache. The wrapper bounds concurrent calls without an unbounded queue, starts an abortable deadline before dispatch, checks declared response length, and counts actual streamed bytes. Each accepted stream chunk is copied before the next read so a transport that reuses its buffer cannot alter already-read response bytes; owned interim chunks are cleared after assembly or failure. It returns only status, content type and bounded bytes. Provider exception text, response bodies and redirect targets do not appear in its errors. Authentication and provider response validation remain the caller's responsibility; a 2xx response alone grants no permission or credential validity.

The current interface permits catalogued GET and POST operations with at most 1 MiB configured request bytes, 8 MiB response bytes, 32 active calls, a 30-second deadline, 32 destinations and five approved header names. Each instance can set smaller limits. The caller must choose limits from the operation's actual cost and must not put secrets in the URL. An integration needing dynamic path segments or query values requires a separate reviewed bounded operation contract; it must not widen a catalog entry to an arbitrary path. Caller cancellation now rejects promptly with a safe `UNAVAILABLE` error even if the transport ignores abort; a late response is cancelled. A cancelled or timed-out transport retains its concurrency slot until its underlying operation settles. This fails closed if a noncooperative transport ignores abort, at the cost of temporarily or permanently exhausting that instance's capacity.

## Destination and egress boundary

The catalog must be assembled from trusted deployment/plugin configuration, not a URL in a public request, stored Issue, webhook payload or redirect. Only reviewed provider hostnames should enter it. The shared wrapper does not itself resolve DNS or provide an egress firewall. A trusted hostname can still be misconfigured or rebound to a private address. The Node-only `createNodeOutboundFetcher` composition uses a direct `https.request` connection with a one-time agent and custom connection-time lookup. It requires every returned A/AAAA address to be a public unicast candidate, selects only one approved address for the socket, verifies the connected remote address, and keeps the original hostname for SNI and certificate verification. It denies mapped/private/link-local/loopback/multicast/reserved/documentation/benchmark addresses and DNS failures. Redirects remain manual through the shared policy; compressed responses are denied instead of silently bypassing byte accounting. This is a conservative direct-egress adapter, not an arbitrary destination or proxy mode.

`createCloudflareOutboundFetcher` in the Workers application explicitly supplies platform `fetch` to the same policy. The shared constructor has no implicit global-fetch fallback, so an omitted transport cannot silently bypass Node's address-pinned adapter. The Workers composition has no custom DNS pinning; effective platform restrictions and the account's egress configuration still require deployed verification. Both production roots now construct the optional Turnstile verifier and retain its public site key in the shared server when complete bindings are present. The registration route publishes the public key and calls the verifier after rate admission; deployed Siteverify behavior remains unverified.

This address classifier cannot prove the host's routing, upstream NAT/firewall behavior, account policy or future IANA registry changes. Operators still need restricted egress and a reviewed exact provider catalog; a proxy deployment needs a separately verified proxy transport rather than an implicit environment-proxy fallback. The Node production root instantiates this adapter only when complete optional Turnstile bindings are present, and registration now uses its configured gate. Workers provider restrictions must be checked against the effective account/runtime and bindings; a private-network binding is a distinct privileged route and is not covered by this wrapper. No dynamic or arbitrary host is enabled by this increment.

Before an integration uses the wrapper, record its exact origin, owner, permitted method/target pairs, DNS and proxy/egress policy, credentials, response validation, retry/idempotency behavior and data classification. Revalidate redirects and DNS at every hop if redirects are ever introduced. Do not use a mocked transport as evidence of real provider reachability or DNS safety.

### Exact operation catalog checkpoint

On 2026-09-26, the catalog began requiring exact GET/POST and relative-target pairs per destination. The optional query string is part of the target, so a caller cannot add, omit or change parameters without a reviewed entry. Construction rejects missing, duplicate, noncanonical or encoded-path entries, and dispatch rejects an unlisted combination before transport use. The local shared tests verify those rejections, allowed GET/POST dispatch and resistance to post-construction catalog mutation; the Node transport fixture declares its two exact GET targets. This is an application-level boundary only. A real provider integration and deployed Node/Workers DNS, TLS and egress evidence are still required for 03.3e and 03.V2.

### Turnstile Siteverify candidate

On 2026-09-26, the first provider candidate declared only `POST https://challenges.cloudflare.com/turnstile/v0/siteverify`. The shared adapter posts form-encoded secret and token in the body, omits optional `remoteip` until trusted ingress exists, makes no retry of a single-use token, and accepts only a bounded 200 JSON response. It normalizes success, hostname, action and challenge timestamp for the independent CAPTCHA gate. A response-token or replay failure denies; a secret/configuration error, unknown error code, malformed JSON or provider outage is unavailable and cannot turn CAPTCHA off. The profile constructors use the Node pinned-address HTTPS transport and the Workers platform transport under this same exact catalog. The provisional local bounds are eight concurrent calls, a three-second outbound deadline, 16 KiB request and 8 KiB response caps; they are not deployment measurements. Production roots select this candidate only with complete runtime bindings. The registration GET publishes the public site key/action and POST uses it after rate admission. A local workerd test now drives the production API through the signed ingress with an injected Siteverify transport: missing token avoids egress, a correctly shaped fixture response admits, and simulated provider outage denies without account storage. This does not prove live Siteverify or deployed Workers egress.

Cloudflare's default, staging and production `secrets.required` lists remain limited to the mandatory key rings; adding `TURNSTILE_SECRET` there would make CAPTCHA setup mandatory. Current [Wrangler configuration documentation](https://developers.cloudflare.com/workers/wrangler/configuration/#secrets-configuration-property) says a configured list filters extra `.dev.vars`/`.env` keys. An opt-in `local-turnstile` environment therefore declares all five required local binding names and retains the local D1/rate-limit resources. `corepack pnpm dev:cloudflare:turnstile` loads an ignored `.dev.vars.local-turnstile` file; Wrangler 4.133.0 displayed all five hidden bindings and the local readiness request returned 200. The temporary fixture file was removed after that check. This proves local binding delivery and startup, not a product-route Siteverify call, deployed Wrangler secret persistence or real provider egress. Do not place the secret in `vars` or ordinary runtime policy.

Context7 resolve-then-query on 2026-09-26 selected the high-reputation [Cloudflare Turnstile documentation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/). It documents the exact POST endpoint, form or JSON body, required `secret` and `response`, optional `remoteip` and `idempotency_key`, `success`/`hostname`/`action`/`challenge_ts` fields, 2048-character token maximum, 300-second validity and single-use replay failure. The [Turnstile Spin reference](https://developers.cloudflare.com/turnstile/spin/) also shows server-side hostname/action comparison. These references establish the provider contract, not this deployment's credential, network reachability, DNS policy or widget behavior.
