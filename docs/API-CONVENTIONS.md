# Public API conventions

The public business API uses `/api/v1`. Its contract is versioned JSON/REST plus OpenAPI, independent of Elysia server types. `packages/contracts` owns reusable schemas and DTOs; module 10 owns validated OpenAPI generation and the public client. No feature endpoint exists merely because it is listed in the [inventory](API-OPERATIONS.md).

## Representations and compatibility

IDs are lowercase UUID strings. Issue numbers and revisions are positive bounded integers. Instants are canonical UTC strings with exactly three fractional digits. Nullable fields are explicitly null; optional fields describe genuinely absent capabilities, not a second encoding of null. Requests reject unknown fields; response consumers must tolerate additive fields. Breaking field meanings, enum removals, narrowing accepted input, or changing ordering semantics requires a versioned contract change. New closed enums need a documented client compatibility strategy.

Use JSON with `Content-Type: application/json` for ordinary writes. Apply endpoint-specific byte, string, nesting and collection bounds before expensive work. The foundation defaults to a 64 KiB JSON byte ceiling and a 10-second cooperative deadline. It also bounds JSON depth (16), values (4096), object keys (128), array items (256), string length (32768), URL length (8192), query parameters including duplicates (64), and decoded query values (2048). JSON container depth is checked before parsing; nonfinite numbers and prototype keys are rejected. See the [security configuration](SECURITY-FOUNDATION.md#configuration-schema) for units and deployment bounds. Upload binaries use the module 07 direct-upload flow. Framework validation details, stack traces, SQL and provider responses are never public error payloads.

## Errors and correlation

Errors have `{ "error": { "code": "STABLE_CODE", "message": "Safe explanation.", "requestId": "uuid" } }`. Every response gets a server-generated `X-Request-ID`, ignoring untrusted client IDs. Errors and health/private/security responses use `Cache-Control: no-store`. Request IDs may appear in logs/audit/traces, but never as metric dimensions. Logs contain no credentials, cookies, request bodies or raw error objects. Expected errors use a closed catalog too; mutable exception messages never become public text. `INPUT_LIMIT_EXCEEDED` and `INVALID_JSON` are 400, `ORIGIN_FORBIDDEN` is 403, and `INVALID_PREFLIGHT` is 400.

`GET /health/live` returns `{ "status": "ok" }`. `GET /health/ready` returns a status of `ok` (200) or `unavailable` (503) plus `deployment: { tier, degradationIds, passwordHashPolicy, bootstrapPending? }`; `bootstrapPending` appears (true when no active Staff administrator exists) only when a staff-enrollment store is configured, and a failed state probe omits the field without failing readiness. The current running tier is `standard`, so its IDs are empty and its required hash policy is `argon2id`. Both production roots report unavailable if abuse admission is unconfigured, its key ring cannot be loaded, the current token-HMAC key cannot be loaded from the authoritative registry and secret source, or the primary counter, password credential, or authorization-session table cannot be queried; Workers also requires its approximate binding to exist. This read-only probe does not prove write permission, trusted Workers ingress, multi-location consistency, password-login availability or full product readiness. The minimum tier still fails startup and cannot produce a readiness response. The readiness schema is additive to the original status field and exposes no secrets or provider quota values.

Rate-limit rejection uses `RATE_LIMITED` (429) and may include an integer `Retry-After` from 1 to 86400 seconds. Counter or key-provider failure, timeout or invalid admission deadline uses `RATE_LIMIT_UNAVAILABLE` (503), without a retry hint. The shared HTTP boundary validates the hint again before emitting it; a route must never copy a provider error message or untrusted header into this response. `POST /api/v1/accounts/register` is the first owned route to enforce these decisions.

`GET /api/v1/accounts/register` returns the public registration challenge descriptor `{ captchaRequired, captchaSiteKey, captchaAction: "register" }` with no verifier secret. `POST` accepts a 3–32 character ASCII handle, a 12–128 character password and an optional `captchaToken`. It canonicalizes the handle to lowercase, consumes account and root-trusted IP rate attempts before any password work, then applies a configured challenge. An absent CAPTCHA provider requires no token. An accepted new or duplicate handle receives the same no-store 202 `{ "accepted": true }`; no credential or Staff grant is returned. Missing account persistence/hash service maps to `REGISTRATION_UNAVAILABLE` (503), while their failure also denies safely. On the enabled minimum tier, where the reviewed parameter floor disables the password surface, registration and password login answer the documented capability error `PASSWORD_CAPABILITY_DISABLED` (403) before any admission or parsing work, matching the instance document's `passwordRegistration`/`passwordLogin: false`. The Node root takes IP from the native socket peer. The Workers root accepts a five-second HMAC assertion from its controlled public service-bound ingress when configured; direct unsigned requests deny with 503. This works in local workerd/D1, while actual edge IP provenance and private routing await deployed verification. This is a narrow registration path, not login, recovery or complete Module 04 capability acceptance.

The optional Free-tier account-lockout guard uses the same closed 429/503 codes. It checks all active account-key versions under a bounded deadline before password verification; lockout state failure, malformed evidence, timeout or cancellation maps to 503. Separate bounded operations record an invalid password and clear a verified success before the route completes. No account route uses these guards yet, and the Free tier remains disabled.

The minimum-tier login admission service orders authoritative account/IP rate checks, D1 lockout and configured CAPTCHA verification, then returns a one-use server-side permit for an invalid-password or verified-success transition. It reuses the same active HMAC key snapshot across rate and lockout; a rate denial makes no CAPTCHA request. The account route still owns trusted subject extraction and generic login responses.

The shared authorization route guard maps current-facts denial to `FORBIDDEN` (403), stale or insufficient assurance to `REAUTHENTICATION_REQUIRED` (403), and resolver failure, timeout or cancellation to `AUTHORIZATION_UNAVAILABLE` (503). These are closed, no-store error envelopes with no resolver detail. A protected action runs only after the guard returns; no product route uses it yet.

CAPTCHA setup is optional. With no provider configured, the shared gate requires no token. A configured provider enables verification by default, with no separate enable flag: a missing or failed challenge maps to `CAPTCHA_DENIED` (403), while malformed configuration prevents construction and stalled, malformed or failed verification maps to `CAPTCHA_UNAVAILABLE` (503). No provider response, token or client-claimed success appears in either error. Registration and login are its current account consumers; it never replaces rate limits or authorization.

Sensitive route implementations receive the shared `sensitiveAdmission` service with its abuse-key provider, approximate limiter and primary counter store bound by the application root. A route supplies its request, trusted non-IP subjects, category rules and the optional CAPTCHA token, never its own key or counter source. The bound service replaces every IP subject with its root-selected address; Node uses the native socket peer, while Workers verifies a configured signed ingress assertion or keeps IP-required categories closed. Missing authoritative dependencies or required IP provenance deny with 503. The service applies approximate load shedding before authoritative rate admission; an approximate allowance never substitutes for primary counters. Approximate denial is 429 without a retry hint, and approximate outage is 503. Rate denial avoids a CAPTCHA provider call; a configured challenge then has its own 403/503 result. A request cancelled during either step cannot reach the protected action, including when no CAPTCHA provider is configured. Registration and login are its current route consumers.

`GET /auth/login` publishes `{ captchaRequired, captchaSiteKey, captchaAction: "login" }`. `POST /auth/login` accepts the same bounded handle/password shape as registration plus an optional challenge token. The login POST requires `Origin` equal to its own origin and, when sent, `Sec-Fetch-Site: same-origin`. The root-selected approximate and primary account/IP login limits and configured CAPTCHA run before password verification. Invalid or unknown credentials return the same no-store `LOGIN_DENIED` (401); missing key, store, rate or session dependency returns a closed 503. Success sets a host-only `__Host-hb_session` cookie with Secure, HttpOnly, Path=/ and SameSite=Lax. `GET /auth/session` validates it against the primary store, including active principal, credential revision, revocation and expiry; `POST /auth/logout` requires the same-origin mutation check, revokes it and clears the cookie. The session endpoint returns only `{ authenticated: true }`. These narrow authorization-service routes do not turn cookies into business API credentials. The session-read and logout routes each consume a distinct root-trusted-IP approximate bucket before session storage; missing limiter or address provenance denies 503, and a shed request denies 429. This protects their session-store work while primary account/IP counters remain authoritative for password login and registration. The full Module 04 login UI, token exchange, rotation and recovery flow remain open.

`POST /auth/authorize` (same-origin, current session required) issues a 60-second single-use authorization code after exact client-id, exact redirect-URI and scope-containment checks against the deployment's registered public clients (`HYPERBUG_OAUTH_CLIENTS`, all-or-nothing configuration; malformed values refuse startup) and the code-flow-only protocol checks: `response_type` must be `code` and `code_challenge_method` must be `S256`, both carried by the request contract and enforced server-side on every authorize and issuance path. The response is the JSON redirect URL carrying `code` and `state`; `S256` is the only accepted PKCE method. `POST /auth/token` (form-encoded; the only non-JSON bodies the boundary accepts) redeems a code — the code is consumed atomically before verification, so a wrong verifier burns it — verifies the S256 challenge with a double-hash constant-time comparison, checks the exact client/redirect binding, and returns `{ tokenType: 'Bearer', accessToken, expiresIn: 600, scope }`; the opaque `at_` token's secret is stored only as a keyed digest. `POST /auth/token/revoke` follows RFC 7009 semantics: unknown, malformed or already-revoked tokens still answer 204 and only dependency failures fail closed. Both token endpoints rate-admit under the `login` category (account keyed by client id / presented token id plus trusted IP, with the `login` CAPTCHA action). Every denial is one generic envelope. The backend-owned authorization pages drive this flow for browsers: `GET /auth/authorize` renders the semantic login form (with the optional configured CAPTCHA widget) or, with a current session, the consent page listing the requested scopes; `POST /auth/authorize/login` (form-encoded, same-origin) authenticates through the shared login admission, sets the first-party session cookie and redirects to the client callback with the code; `POST /auth/authorize/consent` (form-encoded, same-origin, session-authenticated) issues the code the same way. Failures never redirect to unregistered targets — unknown clients, redirect URIs or scopes render an error page on the authorization origin. A protocol-shape rejection of an already-verified client and redirect (`response_type` other than `code`, or a challenge method other than `S256`) is instead redirected back to that verified redirect URI with the RFC 6749 §4.2.2.1 / RFC 7636 §4.4.1 `error` (`unsupported_response_type` / `invalid_request`) and the echoed `state`, before any credential or session work; it never renders an error page. The pages are server-rendered HTML with no scripts (except the Turnstile loader when CAPTCHA is configured), no inline styles, visible labels, described hints, aria-live error regions and a `default-src 'none'; form-action 'self'` CSP widened only for challenges.cloudflare.com; guides `forms` and `accessible-error-announcement` (2026-09-30 retrieval) were applied. The Turnstile loader script is not SRI-pinnable by provider design; the exact-origin script-src pin is the control.

`GET /api/v1/account` is the first bearer-only business API: it accepts exactly `Authorization: Bearer at_<id>.<secret>` (cookies are never credentials on `/api/v1/*`, and no Origin is required so authorized no-Origin API clients stay valid), locates the authoritative token row, verifies the secret against the stored keyed digest under the issuing context, and denies with a closed 401 `AUTHENTICATION_REQUIRED` when the credential is missing, malformed, unknown, revoked, expired or mismatched — or when the principal is no longer active; dependency failures answer a closed 503 `AUTHENTICATION_UNAVAILABLE`. The no-store response is `{principalId, identityId, kind}`. Recent-authentication enforcement stays with the shared authorization guard for the route owners that need it.

`GET /api/v1/account/sessions` (bearer) lists the token principal's active sessions and `DELETE /api/v1/account/sessions/:id` revokes one it owns (foreign or unknown ids answer the same closed 404). `PUT /api/v1/projects/:projectId/members/:principalId` grants or replaces a project role and `DELETE` removes it — both run the shared authorization guard (`role:manage`: administrator membership, assurance ≥ 2 and authentication within the recent-auth bound), and only an active Staff principal can hold a role: membership never converts a User into Staff, so granting to a User principal is forbidden. `POST /api/v1/admin/principals/:id/suspend` and `/activate` flip principal status under the same guard anchored on an administrator project; the last active Staff administrator cannot be suspended, and suspension denies the target's tokens and sessions on their next use. The ceremony mapping is server-side: password login is assurance 1, and a passkey login with required user verification carries assurance 2 while within the recent-authentication bound — a password-issued token therefore answers sensitive administration with `REAUTHENTICATION_REQUIRED` (403) until the administrator steps up. The bootstrap administrator's first project role is seeded out of band (deployment policy); every later grant goes through the guarded API.

`/api/v1/admin/plugins` is the deployment-level plugin registry surface (module 05.2a; plugin ids contain a slash, so item operations carry the id in their JSON body, not the path). `POST /api/v1/admin/plugins` registers a manifest — it is validated against the plugin contract (identity, semver, apiVersion range satisfied by the host, capabilities, extension points, settings, CSP origins) before any row is written; a malformed or incompatible manifest answers `PLUGIN_INVALID` (400), an existing id answers `PLUGIN_STATE_CONFLICT` (409), and success is 201 with the registry summary. `GET` lists the bounded registry (`{plugins: [...]}`), and `POST /api/v1/admin/plugins/load` returns one entry with its validated manifest (unknown ids answer the closed 404). `POST .../enable`, `.../disable`, `.../upgrade` and `.../uninstall` apply the lifecycle: enable requires complete configuration (until the configuration interfaces land in 05.2b, only settings-free plugins can enable — a settings-bearing plugin answers 409), disable is legal only from `enabled`, upgrade keeps the id, requires a strictly higher version and a non-enabled state, and uninstall requires the explicit `policy` `retain` or `delete` over namespaced data (no default; today the registry entry is the plugin's only data). Every endpoint runs the shared authorization guard anchored on an active project the actor administrates under `plugin:install` — a sensitive permission, so password-assurance tokens answer `REAUTHENTICATION_REQUIRED` (403) until the administrator steps up, and non-administrators answer `FORBIDDEN`. Missing registry wiring answers `PLUGIN_UNAVAILABLE` (503). Registry operations are deliberately not audited: module 05's audit scope is suspended by user instruction, so no `plugin.*` audit events exist yet.

These identity and administration mutations are audited: bootstrap enrollment appends `account.enrolled` (system actor `core.identity`), passkey registration appends `account.linked` (metadata kind `passkey`), recovery-code generation and redemption append `recovery.generated`/`account.recovered`, owned session revocation appends `session.revoked`, member role changes append `role.granted`/`role.revoked`, and principal suspension/activation appends `principal.suspended`/`principal.activated` — each after the authoritative write succeeds, correlated by the response's request id into the append-only store with no secrets in metadata. Denied operations append nothing, so the audit trail never becomes an enumeration oracle. A deployment whose audit sink is missing, or whose bounded append fails after a committed mutation, fails the request with `AUDIT_UNAVAILABLE` (503) without compensating the write; the crash window between write and append is that trail's recorded limit.

`GET /api/v1/instance` is the stable unauthenticated capability document: `{ tier, degradationIds, passwordHashPolicy: { algorithm, downgraded }, authentication: { passwordRegistration, passwordLogin, passkeys, recoveryCodes, administratorAssistedRecovery }, limits }`. Password capabilities are advertised only under the standard Argon2id algorithm — the minimum tier's floor-disabled login never presents itself as usable — recovery codes reflect the recovery-store wiring (they remain the recommended path on the minimum tier), passkeys reflect the relying-party configuration, administrator-assisted recovery reflects the staff-enrollment wiring, and `limits.documented` points at the capacity section of [FREE-TIER-PROFILE](FREE-TIER-PROFILE.md). Clients must never imply a capability the document does not report; the OpenAPI consolidation is 10.1a scope.

`POST /auth/bootstrap/enroll` is the operator-channel one-time enrollment for the initial Staff administrator. It requires the same-origin mutation check, consumes registration-class account/IP admission before any work, then verifies the deployment's high-entropy enrollment code (`hbbs1_` + 256-bit base64url) in constant time after hashing; a configured CAPTCHA provider additionally requires a `bootstrap` action token. The Node root arms the route from a private `HYPERBUG_BOOTSTRAP_FILE` mount and the Workers root from the optional `HYPERBUG_BOOTSTRAP_ENROLLMENT` Secret; absent disarms (503 `BOOTSTRAP_UNAVAILABLE`) and a present-but-malformed value refuses startup. Enrollment succeeds only while no active Staff principal exists, creates exactly one Staff principal with a local-password identity and its profile's credential record atomically (the conditional insert makes it single-shot against concurrent calls), and issues no session — the administrator then signs in through `POST /auth/login`, whose local-password lookup and session validation accept both `user` and `staff` principals. On the enabled minimum tier, where password login is floor-disabled, enrollment instead issues the first-party session cookie directly so the operator can register a passkey and recovery codes immediately; the response body is unchanged. A wrong code, an already-used handle and an existing active Staff administrator all answer the same generic no-store 403 `BOOTSTRAP_FORBIDDEN`; the code is never logged or echoed. Local-password identities remain globally unique per handle, so a Staff handle can never equal a User handle.

`POST /auth/recovery-codes` (same-origin, current session required) generates a fresh set of ten single-use recovery codes for the signed-in identity and returns the plaintext values exactly once; only versioned keyed digests are stored, and regeneration deletes the previous generation entirely. `POST /auth/recover` redeems one code: it requires the same-origin mutation check, consumes `password-reset`-category account/IP admission and an optional configured CAPTCHA (`password-reset` action) before any work, verifies the code against the stored keyed digests sequentially, and on a match consumes it atomically, replaces the password at its observed revision and revokes every active session of the principal. Unknown handles run a decoy digest verification for timing parity. Unknown handle, wrong or already-used code, stale-generation code and a revision race all answer the same generic no-store 403 `RECOVERY_DENIED`; a consumed code stays consumed even when the later replacement loses its race. No session is issued on recovery — the account signs in again with its new password.

Passkey routes exist on the authorization origin when the deployment configures the public relying-party values (`PASSKEY_RP_ID`, `PASSKEY_RP_NAME`, `PASSKEY_ORIGIN`; all three or none, and a complete selection without the session/key prerequisites refuses startup). `POST /auth/passkey/register/options` (current session required) issues discoverable-credential registration options with required user verification and stores the single-use challenge bound to the session identity; `POST /auth/passkey/register` verifies the response (challenge, origin, RP ID, user verification), stores only the public key/counter/transports/device state, and returns `{ registered: true }`. `POST /auth/passkey/login/options` stores an anonymous single-use authentication challenge; `POST /auth/passkey/login` rate-admits under the `login` category (account dimension keyed by credential id plus trusted IP and the `login` CAPTCHA action), consumes the challenge, verifies the assertion with required user verification, advances the replay counter (clone-regressed counters deny), and issues the first-party session cookie through the same revision-bound issuance as password login — the passkey itself never leaves the authenticator and no secret is stored. Failures answer generic no-store 403 `PASSKEY_DENIED` (or 503 `PASSKEY_UNAVAILABLE` when unconfigured).

## Browser origins and cache

Any present Origin must exactly match the explicit deployment allowlist; null, wildcard and lookalike origins are denied. No-Origin clients remain eligible for normal authentication and authorization. Business APIs do not enable credentialed cookies. Preflight methods and headers are explicit; the maximum preflight age is 300 seconds. Preflights vary on Origin, Access-Control-Request-Method and Access-Control-Request-Headers; actual responses vary on Origin and expose x-request-id, retry-after and etag. A preflight does not authorize an operation. All currently implemented routes enforce no-store after handler responses and on errors, including native `Response` headers; future shared caches require explicit anonymous-public representation policy. See [HTTP security policy](SECURITY-FOUNDATION.md#http-errors-and-diagnostics).

## Mutations and concurrency

Every mutable resource carries a revision. Update commands include `expectedRevision`; adapters compare it atomically. A mismatch returns `REVISION_CONFLICT` with a safe refetch instruction, never silently overwrites the newer resource. Successful writes return the new representation and revision. Server clocks own timestamps.

Endpoints that support retries require `Idempotency-Key` (16–128 ASCII letters, digits, hyphens, underscores). Scope, payload matching and expiry follow [DATA-MODEL](DATA-MODEL.md). Authorization is evaluated on every attempt including replays. A replay may return the prior snapshot, identified by `Idempotency-Replayed: true`; clients can explicitly refetch current state. Secrets and signed capabilities must not be stored in replay snapshots. Unsupported idempotency behavior must be documented per endpoint; never advertise replay safety for external effects before outbox acceptance.

## Cursor pagination

Collections default to 40 items and cap at 100; an endpoint may impose a stricter bound. Clients pass `limit` and `after`, treat `after` as opaque, and receive `{ items, nextCursor }` where `nextCursor` is null at the end. No unlimited list and no deep offset pagination exist. Lists exclude full Markdown/HTML/tree bodies; module 07 supplies bounded plain-text previews under the [content plan](plan/modules/07-content-and-attachments.md). Detail representation and rendering never change cursor boundaries.

Version 1 cursors encode a bounded base64url JSON envelope containing version, resource, project, normalized filter/sort fingerprint and the last item's immutable sort tuple. Initially the Issue sort is `created_at DESC, id DESC`. Decode validates byte size (maximum 1024), exact known fields, version, UUID/time types and the supplied resource/project/filter/sort. Mismatches are `INVALID_CURSOR` (400), not a silent first-page restart. These non-secret cursors are not authorization capabilities; every page reauthorizes project/object visibility. User tampering can select a different boundary only within the same authorized query, never inject SQL or expand bounds. A future cursor carrying a protected snapshot must be authenticated with a reviewed MAC before use.

A deleted boundary item does not invalidate the tuple; use strict keyset comparisons. Inserts after the previous page's newest boundary appear on a refresh, not later pages. Deletions may shorten a page. Mutable filters can change membership between pages; v1 provides a live traversal, not snapshot isolation. If a version/sort policy is retired, reject the old cursor as `CURSOR_STALE` (400) and instruct refresh. Equal timestamps always use the ID tie-breaker.

## Visibility, authentication and deprecation

[API-OPERATIONS](API-OPERATIONS.md) defines the minimum permission matrix. Public User and Staff identities are separate. Browser bearer credentials remain memory-only; no new auth flow or browser token store is introduced by these conventions. Authentication, CSRF/CORS, assurance and revocation implementation belongs to modules 03–04; the protocol specification is [AUTH-FLOWS](AUTH-FLOWS.md).

A hidden project/resource yields the same safe 404 as a missing one where existence would disclose information. Moderated content is excluded from public detail, lists, search, history and event metadata. Cross-project references require authorization to both sides and an explicitly accepted feature policy; initial writes disallow them.

Additive changes are documented with release notes and OpenAPI diffs. Deprecations publish migration guidance and an announced removal policy before a breaking version is released; this foundation invents no arbitrary calendar SLA. Module 10 adds consumer compatibility tests and owns readiness to publish the API.
