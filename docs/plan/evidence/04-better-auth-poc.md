# Better Auth candidate PoC (04.1b)

Date: 2026-09-30. Owner: [04.1b](../modules/04-identity-and-access.md). Scratch workspace: `.local/phase04-betterauth-poc/` (ignored, local-only; not production code). The selected business framework is unchanged by this PoC.

## Scope and method

Better Auth `1.7.6` with `@better-auth/oauth-provider` `1.7.6` (same-day release line), verified against both required profiles:

- **Node 24.21.0 / PostgreSQL 18.6** (isolated private Unix-socket cluster via the repository's `tooling/postgres-test-cluster.mjs`): real HTTP server wrapping `auth.handler`, schema generated by `@better-auth/cli generate` and applied to the live database, 20 checks (`results-postgres.json`, 16 pass).
- **workerd + D1** (Miniflare with a D1 binding, `nodejs_compat`, compatibility date 2026-08-06): esbuild bundle (≈2.8 MB) driving the same flow through `dispatchFetch`, 11/11 checks (`results-d1.json`).

Configuration under test: `emailAndPassword`, custom `__Host-` session cookie, `oauthProvider({ disableJwtPlugin: true, codeExpiresIn: 60, accessTokenExpiresIn: 600 })`, public client (`token_endpoint_auth_method: "none"`), full Authorization Code + PKCE S256 flow including consent. Context7 lookups (2026-09-30, `/better-auth/better-auth`, three queries: oauth-provider setup, opaque tokens/revocation, session/D1) plus direct inspection of the installed 1.7.6 packages.

## Verified capabilities (both profiles)

- **Protocol**: authorize endpoint accepts `response_type=code` + `code_challenge_method=S256` (the only supported method); public clients always require PKCE; redirect URIs are exact-match and **web clients are forced to https non-loopback** (http loopback is reserved to native clients); `state` round-trips; consent flow issues the code; the authorize/consent endpoints answer JSON redirect envelopes (`{"redirect":true,"url":...}`) rather than raw 302s — the login/consent pages are deployment-supplied paths.
- **Code properties**: `codeExpiresIn: 60` honored; wrong verifier → 401 and the code is consumed; code reuse → 400; a recorded consent later skips the consent page.
- **Opaque tokens**: with `disableJwtPlugin: true` the access token is a 32-character base62 string (no JWT structure); `expires_in: 600` honored; stored server-side as a **hash** (43-char base64url ≈ SHA-256), never verbatim.
- **Revocation**: `POST /oauth2/revoke` with form `client_id` (public client, no secret) removed the token row and the bearer was denied afterwards on both profiles. Session sign-out revoked the session on both profiles.
- **Storage**: auto-detection of a raw `pg` Pool (kysely path) and of a D1 binding (documented `batch()` atomicity) both worked; the CLI generated the full 11-table schema (core + oauth provider models).
- **Session cookie**: name and attributes configurable; `__Host-` prefix with Secure/HttpOnly/Path=/SameSite=Lax verified emitted on both profiles; cookie value is `<32-char id>.<HMAC signature>` and the full value is not stored server-side.

## Gaps and deviations found

1. **Token entropy below baseline**: the default opaque token is 32 base62 characters ≈ 191 bits, below the required ≥256-bit secret. A `generateOpaqueAccessToken` hook exists to supply a stronger generator.
2. **Unkeyed digest by default**: `storeTokens` hashes with plain SHA-256, not a keyed HMAC; a custom `{ hash }` function can be injected. Both fixes are configuration, not code.
3. **Session storage model differs**: Better Auth stores a plaintext 32-char session id and binds an HMAC signature into the cookie; HyperBug's contract stores a keyed digest of a ≥256-bit cookie secret. Better Auth's sign-in response body also includes the raw session token, which HyperBug would have to suppress.
4. **Session lifetime model**: single absolute `expiresIn` plus `updateAge` refresh; no native separate idle+absolute columns.
5. **Introspection is confidential-clients-only** (client secret or pre-verified required; code-confirmed). A resource server instead uses the internal `validateOpaqueAccessToken`-style lookup.
6. **`/oauth2/userinfo` rejected the public-client opaque token** (`invalid_token`) in the `disableJwtPlugin` configuration on PostgreSQL even with the token row present and unexpired — needs upstream investigation before any adoption; the equivalent library-level validation path exists and is sound.
7. **Cross-profile status inconsistency**: `/oauth2/revoke` for the same public client returned 200 on workerd/D1 but 400 on PostgreSQL while producing the same functional effect (row removed, bearer denied).
8. **Workers packaging friction**: the kysely adapter's variable-specifier dynamic `import(nodeSqlite)` breaks workerd module resolution and required an esbuild patch; `node:async_hooks` and `node:module` resolution require `nodejs_compat`; `@opentelemetry/api` must be present; the bundle is ≈2.8 MB.
9. **Dependency conflict**: better-auth 1.7.6's bundled drizzle adapter requires `drizzle-orm ≥ 0.45.2`; the workspace pins 0.44.7, so adoption would drag a maintenance-scope upgrade. The PoC exercised the kysely (raw pg/D1) path, not the drizzle adapter.
10. **CSRF posture**: POST endpoints reject missing Origin (`MISSING_OR_NULL_ORIGIN`) — compatible with HyperBug's same-origin cookie-flow posture but stricter than our no-Origin API-client rule for the auth surface.

## Outcome

**Candidate not accepted for adoption; the selected business framework is unchanged.** The protocol, opaque-token mechanism and revocation work on both profiles, but the session/storage rules deviate from the HyperBug baseline in entropy defaults, digest keying, session-token model and the opaque-userinfo gap, and adoption would force a drizzle-orm upgrade plus Workers build patching. Per [TECH-STACK §42](../../initial-architecture/TECH-STACK.md), authorization, roles, project permissions and Staff identity remain Core-domain work regardless. The PoC is recorded for future reconsideration if the upstream gaps close; nothing here blocks the Core-owned 04.2 implementation.
