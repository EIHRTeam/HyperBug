## Behavior and boundaries

`POST /api/v1/accounts/register` first applies trusted-IP approximate shedding before parsing. It then validates a bounded handle/password body, canonicalizes a lower-case ASCII account subject, and calls the root-bound sensitive admission with account and root-selected IP checks. The provisional primary budgets are five account attempts and 20 IP attempts per 60 minutes; the admission deadline is 1,000 ms. Approximate shedding cannot replace primary counters. A complete optional Turnstile configuration adds required `register` action verification after rate admission. No provider means no challenge token is needed. Only an allowed attempt reaches the standard-profile Argon2id service and the atomic User/identity/credential store. New and duplicate handles receive the same 202 response. No session or Staff privilege is created. `GET` on the same path exposes only the selected public site key and action.

Node selects its native socket peer; forged forwarding headers are ignored. The production Workers root deliberately supplies no IP resolver, so IP-required registration returns 503 even with D1 and an abuse key. The local workerd functional fixture injects a constant test-only trusted address. This fixture establishes route/adapter behavior, not deployed ingress trust. Key/counter/CAPTCHA/provider errors deny before account writes; missing hash/store dependencies and hash/store failure return a closed 503.

## Internal verification and rehash follow-up

The internal `verifyAccountPassword` operation now loads an active User credential, verifies it with the root-selected standard password service, persists a returned replacement at the observed revision, and reloads the credential before returning an identity and revision to a future session issuer. An unknown handle performs a selected-policy dummy hash before returning no identity; a wrong password returns no identity; stale revision, store outage and missing dependencies fail closed. The future issuer must revalidate the returned revision and account status when creating an authorization session. This operation is not a public login route and issues no token or cookie.

Focused unit verification passed 4/4 for replacement ordering, unknown/wrong credentials, stale replacement, suspension, final-read account change and outage. The same operation passed focused isolated PostgreSQL 18.6 and local workerd/D1 repository cases 1/1 each with a fixture verifier and real conditional storage; TypeScript, lint/boundaries and scoped formatting passed. This does not prove an actual login flow, provider performance, timing equivalence, live D1 or deployed authorization. 03.2e and Module 04 remain open. The Module 04 dependency analysis is that returning a usable login credential requires its first-party authorization session or opaque token contract; a bare boolean response would not be a functional login and could disclose credential validity. The public route remains closed until that contract exists.
