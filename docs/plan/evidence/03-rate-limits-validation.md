# Phase 03 rate-limit foundation validation

Started: 2026-09-25; updated: 2026-09-26. Scope: 03.3c and the non-audit part of 03.3d, both partial. Decision: [ADR 0008](../../decisions/0008-rate-limit-consistency.md). The current module and 03.V3 remain open.

## Changed behavior and storage

- Shared security contracts define the ten source-required categories, six dimensions, a versioned domain-separated HMAC subject digest, fail-closed sensitive decisions and whole-second retry hints. Callers must use a dedicated non-extractable HMAC key and canonicalize subjects at a trusted boundary.
- D1 and PostgreSQL migration `0007_rate_limits` add only `rate_limit_counters` and an expiry index to their separate 0000–0006 histories. Composite keys isolate category/dimension/key version/digest/window. Both adapters use one primary-write upsert with `RETURNING`; a subsequent shorter retention value can shorten an existing row expiry but never extend it. Bounded purge deletes at most 1,000 expired rows per call.
- The Node process-local and Cloudflare Rate Limiting binding adapters are explicitly approximate volumetric mechanisms. Neither is wired to a product route or is the sole gate for a sensitive operation.

## Focused review and limits

The upsert is a write on D1's primary, so admission does not depend on an asynchronously replicated read. PostgreSQL locks conflicting upsert rows. Raw IPs, account names and tokens are not persistence columns; the HMAC includes category and dimension to avoid cross-purpose correlation. The exact caller key source and proxy/IP canonicalization are not integrated. Fixed windows can permit boundary bursts, so sensitive route owners must compose appropriate dimensions and windows. A failed store returns `unavailable`, which the future route must deny. Bounded cleanup is implemented but not scheduled; expiry metadata alone does not enforce physical retention.

Cloudflare's binding is location scoped and eventually consistent. Its adapter was tested with a fake binding only; no real account, Free tier, multi-location request, provider outage, Node multi-process proxy, login route or CAPTCHA path was exercised. 03.3c–03.3d and 03.V3 remain unchecked until the actual route/configuration and consistency matrix exists. The optional minimum tier remains unavailable, and Argon2id performance exploration and audit work remain stopped.

Context7 resolve-then-query on 2026-09-25: [D1 read replication/primary writes](https://developers.cloudflare.com/d1/best-practices/read-replication/), [PostgreSQL 18 `INSERT`/locks](https://www.postgresql.org/docs/18/sql-insert.html), [Drizzle schemas/migrations](https://orm.drizzle.team/docs/migrations), and [Workers Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/). Installed SQL and local runtime checks are separate evidence from these documentation claims.

## Bounded route admission (03.3c/03.3f partial; 2026-09-26)

`requireSensitiveRateAdmission` now requires an explicit 10–5,000 ms deadline for the complete key-source, digest and primary-counter decision. It reuses the server's abortable `withDeadline` boundary and maps timeout/cancellation to `RATE_LIMIT_UNAVAILABLE` (503), never a successful admission or a 429 retry hint. Invalid/missing budget is rejected before the key source or counter is called. A provider or store that ignores abort may continue its pending work after the HTTP denial; the route's protected action does not run, and an already-dispatched counter increment may complete later. ## Deployed approximate-budget burst observation (2026-09-30)

A no-provider gateway/API pair on `gw-ld0a54047.test.eihrteam.org` (same fixed-gateway composition, Workers Rate Limiting binding configured at the provisional 1,000/60 s simple budget) absorbed a controlled synthetic burst of unauthenticated `GET /auth/session` requests from the authorized oci host: 1,300 requests in 2.3 seconds (~560 rps, HTTP/2 multiplexed) returned **1,023×401 and 277×429** — the deployed approximate shedding boundary enforcing at the edge for the first time (previously proven only with local two-slot Miniflare fixtures). A slower control burst (1,100 requests over 93 seconds, ~12 rps with per-request handshakes) never exceeded the window budget and returned 401 throughout, and after a 65-second window pause three further requests were admitted again.
