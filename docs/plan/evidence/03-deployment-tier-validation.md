## 03.V7 Free-plan PBKDF2 measurement and floor decision (2026-09-29)

Under the Module 03 audit/tier resume with the user-asserted Cloudflare Free account, a temporary capability-guarded Worker (`hyperbug-phase03-pbkdf2-measure`, deleted after the run; its URL now 404s) measured real-plan PBKDF2-HMAC-SHA256 feasibility. One derivation ran per invocation so each request carried its own full per-invocation CPU budget; because `Date.now()` does not advance during workerd computation, feasibility (success versus a runtime CPU kill), not in-worker timing, is the observable. Raw observations: [measurement artifact](03-free-pbkdf2-measurement.json).

- Coarse ladder: 1,000–100,000 iterations succeed (3/3 each); 150,000–600,000 fail (0/3 each).
- Fine ladder: **100,000 succeeds 5/5; 100,500 fails 0/5** — a sharp, deterministic cliff. The per-invocation CPU budget accommodates ≈100,000–100,499 iterations of a 256-bit PBKDF2-HMAC-SHA256 derivation plus negligible framework overhead (≈10 ms CPU at ≈100 ns/iteration).
- Linearity: 10×10,000, 5×20,000 and 2×50,000 (total 100,000) all pass 5/5; the budget is total-CPU with uniform per-iteration cost.

**Security-review floor decision (recorded 2026-09-29):** the reviewed floor for PBKDF2-HMAC-SHA256 on this tier is **600,000 iterations**, following the OWASP Password Storage Cheat Sheet's current recommendation for this primitive; no weaker figure is acceptable for a public-facing credential store. The measured plan ceiling (≈100,000) is six times below the floor. Applying the specification's floor rule ([FREE-TIER-PROFILE](../../FREE-TIER-PROFILE.md), FREE-01): **the minimum tier must not offer password login, and its capability document must report `passwordLogin: false`** until plan limits or the primitive change. Publishing a weaker hash is not an acceptable outcome; this decision is the tier's designed degradation path, not a baseline relaxation. The PBKDF2 mechanism itself remains correct for stored-record verification within the measured budget, and passkey/recovery-code alternatives remain the tier's credential path in their owning module.

**Policy values fixed from this measurement:** verification maximum for stored records = 100,000 iterations (the measured deterministic fit); new-record current policy = 50,000 iterations (≈50% CPU margin for the rest of a real login invocation's work). These bound the existing minimum-password mechanism; wiring them as the tier's deployment policy and the `passwordLogin: false` outcome is the 03.2g implementation increment. The applicable audit/log retention observation on the plan is the 03.3a deployed audit append, which completed within the same per-invocation budget on this account's `hyperbug-test-1`.

**03.2g wiring (2026-09-29, commit `96ec3e2`):** the measured values are fixed in code — `minimumTierPasswordPolicy` (current 50,000 / maximum 100,000) and `minimumTierPasswordFloorIterations` (600,000) in `packages/security/src/minimum-password.ts`, with the executable floor rule `minimumPasswordLoginAvailable` whose measured outcome `minimumTierPasswordLoginEnabled` is `false`. The Cloudflare tier adapter refuses any policy whose current or maximum exceeds the measured 100,000 ceiling, so a misconfiguration cannot exceed the Free CPU budget on every verification. Unit cases cover the frozen values, the floor rule both ways, malformed policies and the ceiling refusal. The tier still refuses startup pending its remaining mechanisms and independent acceptance; capability-document surfacing of `passwordLogin: false` belongs to the 04.1e journey.

**03.3h acceptance (2026-09-30, commit `f2194d5`):** the minimum tier's compensating abuse controls are complete to module 03's boundary. The D1-backed lockout and progressive delay now have chosen parameters (`minimumTierAccountLockoutPolicy`: 500 ms initial delay doubling every two failures, 15-minute cap and streak reset); per-account and per-route quotas use the shared admission mechanisms with the declared classification; required-when-configured Turnstile is the existing gate; administrator alerting is a bounded digest-only emitter (`createLockoutAlertEmitter`) wired into the minimum login admission's failure transition — at most one alert per subject digest per ten-minute suppression window, per-isolate tracking capped, best-effort so a sink failure never affects admission; and `minimumTierLimitConsistency` declares which limits are consistent (D1 lockout, authoritative admission counters) and which are approximate (volumetric shedding, alerts), decided against the measured write budget. Alert delivery and the tier's runtime activation belong to later modules and 13.G6.
