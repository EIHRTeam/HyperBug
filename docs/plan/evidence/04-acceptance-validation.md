# Module 04 acceptance evidence (04.V1–04.V4, 04.V6 executable parts)

Date: 2026-10-01. Owner: [module 04](../modules/04-identity-and-access.md). 04.V5 stays suspended. All evidence below ran on Node 24.21.0 with the repository's private PostgreSQL 18.6 cluster (Profile B) and Miniflare/workerd with D1 (Profile A), except the browser fixture which ran against the Node profile.

## 04.V1 — redirect/code/token flow, HTTP harness + browser fixture

- HTTP harness on both profiles: the PostgreSQL and workerd oauth suites drive the complete journey — registration, login (session cookie), `POST /auth/authorize`, code exchange at `POST /auth/token` (`at_` token, `expiresIn: 600`), replay denial, revocation — plus the backend-owned page flow (`GET /auth/authorize` → login form → `POST /auth/authorize/login` → 302 with `code`/`state` → exchange; consent page with an existing session → `POST /auth/authorize/consent` → second code). Local origins on both profiles are separate (Node listener origin vs the registered `localhost:5173` callback; workerd `auth.poc.example` vs `app.poc.example`).
- Browser fixture (Chrome via the DevTools MCP, isolated context): on the separate origins `http://localhost:8787` (authorization service) and `http://127.0.0.1:9999` (SPA-standin callback), the authorize page rendered and the login form POSTed (the server's response body rendered in-browser on a denial case, proving navigation); the server's cross-origin 302 to the callback with `code` and `state` is proven by direct request (curl) and both suites. This automation Chrome refused to FOLLOW a cross-origin redirect after a form POST (`net::ERR_ABORTED`, server log confirms zero arrivals) — recorded as a browser-automation limitation, not a server defect. On the same-origin registered callback the full browser journey completed: login form → 302 → callback URL carrying `code`+`state` → exchange issued a Bearer `at_` token; the consent page then rendered directly from the existing session (no re-authentication), matching AUTH-FLOWS' refresh path.
- Third-party cookies: none are read or set anywhere in the flow — the first-party `__Host-` session cookie is scoped to the authorization origin and the code travels by redirect; the browser ran with its default cookie settings and no third-party context was involved.

## 04.V2 — negative protocol cases

Covered in `tests/postgres/oauth-route.test.ts` (third journey) and the earlier suites, server-side enforced: wrong PKCE verifier burns the code (400), code replay after use (400), redirect mismatch on exchange (400), expired code after a real 61-second wait (400 `OAUTH_DENIED` — no clock injection), unknown client/redirect/scope renders the authorization-origin error page (400 HTML), revoked token denies on the account API (401), and session fixation is prevented by login-minted identifiers (two logins issue distinct cookies; recovery revokes every session). Missing/wrong `state` is the SPA's client-side check by design (the server echoes `state` opaquely and the fixture verifies round-tripping).

## 04.V3 — principal classes and role behavior

Covered in `tests/postgres/roles-route.test.ts` (second journey) plus the first: anonymous (401 `AUTHENTICATION_REQUIRED`), User (bearer account API works; can never hold a project role — grant to a User is forbidden), Triage-seeded Staff via the guarded API (second staff principal seeded directly, as bootstrap is single-shot; the triage-holder is below the administrator floor for `role:manage`), administrator (grants/replaces/removes roles after passkey step-up), cross-project isolation (the administrator of project A is forbidden on project B), permission removal (after role deletion even the stepped-up token is forbidden), suspension (suspended principal's tokens deny 401 immediately; activation restores; last-active-staff protection), and recent-authentication (password tokens answer `REAUTHENTICATION_REQUIRED` until the passkey ceremony). Same-email User/Staff is structurally impossible: principals carry no email and identities are keyed by provider+issuer+subject with global handle uniqueness.

## 04.V4 — no-Origin clients and disallowed origins

A valid bearer request without any Origin header succeeds on `/api/v1/account` (both suites), while the same token with `Origin: https://evil.example` is rejected 403 `ORIGIN_FORBIDDEN` by the shared boundary; the cookie-flow endpoints additionally enforce same-origin Origin/Sec-Fetch-Site (page suites and login fixtures).

## 04.V6 — executable parts

The instance capability document is served on both profiles and its flags derive from composed state: password capabilities advertise only under the standard Argon2id algorithm (the floor-disabled minimum tier can never present password login as usable), passkeys reflect the relying-party configuration (asserted true in the workerd passkey fixture and false without configuration in the postgres bootstrap fixture), and `limits.documented` anchors the FREE-TIER-PROFILE capacity section (pinned by test). The tier stays startup-disabled; the tier journey items (registration/login/recovery under PBKDF2, administrator-assisted recovery on the tier, degradation-notice reachability) remain on the activation path per the goal's boundary, and no enabled-tier claim is made.

## Addendum (2026-10-01) — post-acceptance defect fixes

Recorded under the user's decision not to reopen the acceptance items: the defects below were found by the post-acceptance review over `aa6795a..c39473c` and fixed with incremental evidence rather than a re-run of the acceptance matrix.

- Defect #1 (telemetry mislabeling, fixed in `facb87b`): the `jsonTelemetry` route allowlist omitted `account.account`, so `/api/v1/account` traffic serialized as `unmatched`. Fix: `ROUTE_LABELS` in `@hyperbug/observability` is now the single frozen source for the `RouteLabel` type, the server's route matching and the serialization allowlist, making the gap structurally impossible. A forgotten debug no-op in passkey login verification was removed in the same commit. Verification: unit+contract 111, node 50, workerd 121, isolated PostgreSQL 18.6 68; typecheck, lint/boundaries.
- Defect #2 (authorize validation gap, fixed with this addendum): the authorize step never enforced `response_type=code` / `code_challenge_method=S256` literals (the request schema did not carry the fields; a doc comment wrongly claimed upstream enforcement). Fix per the user's decision A: `validateAuthorizeQuery` enforces both literals after the client/redirect/scope registry check, every issuance path re-checks them, the request contract carries both fields through, and a protocol-shape rejection of an already-verified client/redirect redirects back to the verified redirect URI with the RFC 6749 §4.2.2.1 / RFC 7636 §4.4.1 `error` (`unsupported_response_type` / `invalid_request`) plus `state`, before any credential or session work — never an error page. New regression cases on both profiles: JSON `response_type=token` and `code_challenge_method=plain` deny 400 `OAUTH_DENIED` with zero stored codes; the page GET, login POST and consent POST each redirect the RFC error (no code, no cookie) while the positive journeys are unchanged. Verification: unit+contract 111, node 50, workerd 121, isolated PostgreSQL 18.6 68; typecheck, lint/boundaries.
- OAuth consistency note for 04.V2: the authorize-side `code`-flow-only / S256 enforcement was completed after acceptance; the 04.V2 negative-protocol evidence above predates it, and the new rejection cases extend it rather than replacing it.
