# 04 — Authentication, identity, and project authorization

Phase: MVP backend  
Prerequisites: 03 complete.  
Progress: [Session log and current status](../progress/04-identity-and-access.md)

## Outcome and scope

Provide a working authorization service and account/project permission system without depending on the SPA or an installed SSO/email plugin.

**Execution override (2026-09-21, Module 04 portions lifted 2026-10-01): [audit suspension register](../AUDIT-SUSPENSION.md). The Module 04 audit portions (`04.3a` linking, `04.3c`, `04.V5`) were resumed by the user's 2026-10-01 instruction and are complete; audit portions of later modules remain suspended.**

**Password-login direction (2026-09-25):** Implement and expose password registration/login/recovery on the standard profiles as part of this module. Independent audit may be deferred or run in parallel and never blocks development or password-login enablement. Further Argon2id performance testing remains stopped. The optional Free minimum tier remains subject to its separate PBKDF2 parameter-floor and acceptance requirements. See [ADR 0009](../../decisions/0009-standard-password-login.md).

**Deferred Phase 03 scope owned here (2026-09-30 re-scope):** the recovery and token rate-limit categories and their measured budgets deferred from 03.3c/03.3d are implemented with this module's owning routes — recovery with 04.2f, token activity with 04.2b/04.2e, privileged operations with 04.3c — using the frozen category-dimension policy from module 03. Production budget numbers are measured under the staging real-load budget milestone, not inferred from local fixtures.

### Step 04.2 — Implement cross-site authorization

- [x] **04.2a** Implement Authorization Code + PKCE S256, fresh high-entropy state/verifier, exact redirect allowlists, client/challenge binding, and short-lived single-use codes (initial target at most 60 seconds). Accepted 2026-09-30: `POST /auth/authorize` (session-authenticated, exact client/redirect/scope registry matching, keyed-digest codes, 60-second bounded lifetime) and `POST /auth/token` (atomic consume-before-verify, double-hash constant-time S256 comparison, exact client/redirect binding) are implemented on both profiles with the deployment client registry (`HYPERBUG_OAUTH_CLIENTS`, all-or-nothing); see [API conventions](../../API-CONVENTIONS.md).
- [x] **04.2b** Implement short-lived opaque access tokens with at least 256-bit random secrets, keyed digest storage, expiry, immediate revocation, and a default lifetime of 10 minutes within the documented 5–15 minute range. Accepted 2026-09-30: `at_`-prefixed tokens (256-bit `hb1_` secret, keyed digest context-bound to the token id, 600-second CHECK-bounded lifetime) with primary-backed loading and RFC 7009 `POST /auth/token/revoke` semantics are implemented on both profiles.
- [x] **04.2c** Implement first-party authorization-session cookies with Secure, HttpOnly, host scope, Path=/, and SameSite=Lax; add cookie-flow CSRF defenses, idle/absolute expiry, fixation protection, and rotation. Accepted 2026-10-01 by assessment: the cookie contract (`__Host-hb_session`, host scope, no Domain attribute) with same-origin Origin/Sec-Fetch-Site checks on every cookie mutation, 30-minute idle plus 7-day absolute expiry, and login-minted fresh identifiers (fixation protection) have existed since the Phase 03 dependency and are regression-covered; the implemented rotation mapping is: login and passkey step-up mint a fresh session identifier, account recovery revokes every session (strictly stronger than rotation), and no in-session password-change flow exists (password changes run through recovery). The remaining SECURITY §18 triggers (privilege escalation and staff role change on a live cookie session) attach to cookie-session-driven administration that the implemented management APIs exercise through bearer tokens; a future cookie-session management surface must rotate on those triggers, recorded as a standing invariant rather than an open implementation gap.
- [x] **04.2d** Provide the authorization-service login/consent/account interaction needed to exercise the flow before the SPA. Any HTML for these backend-owned flows must use modern-web-guidance and the security/accessibility baseline. Accepted 2026-09-30: `GET /auth/authorize` renders the no-JS semantic login form (optional configured CAPTCHA widget) or consent page, and the form-encoded same-origin `POST /auth/authorize/login`/`POST /auth/authorize/consent` endpoints complete the browser flow to the code callback; failures render on the authorization origin. Guides `forms` and `accessible-error-announcement` applied (visible labels, described hints, aria-live errors, `default-src 'none'; form-action 'self'` CSP widened only for challenges.cloudflare.com; the Turnstile loader is not SRI-pinnable by provider design, exact-origin script-src pinning is the control).
- [x] **04.2e** Implement bearer authentication for business APIs, no-store token/account responses, logout/revocation, and recent-authentication checks. Keep business API requests independent of cookies and frontend proxies. Accepted 2026-09-30: `authenticateBearer` verifies the opaque token against the authoritative row and keyed digest under the issuing context (generic 401 for every missing/malformed/unknown/revoked/expired/mismatched case, closed 503 only on dependency failure) and `GET /api/v1/account` is the first bearer-only consumer — cookies rejected as credentials, no Origin required, active-principal enforcement, no-store account response; token logout/revocation is the 04.2b RFC 7009 endpoint and recent-authentication enforcement remains with the shared authorization guard for route owners that need it.
- [x] **04.2f** Implement one-time account verification/reset tokens and enumeration-resistant responses when those account features are enabled; verify invalidation after use and session revocation after recovery. Accepted 2026-10-01 by assessment: the enabled feature set is the no-email deployment, and its reset path is the single-use recovery-code journey — CSPRNG 256-bit codes stored only as keyed digests, account-bound, atomically single-use (invalidation after use proven), enumeration-resistant (identical generic denials for unknown handle, wrong, stale and used codes, with timing-parity decoy work), and recovery revokes every session of the principal. Email-channel verification/reset tokens are part of the email plugin (module 16) and are not enabled in any current deployment; when that plugin lands, its token routes must reuse this exact single-use/enumeration-resistant contract, recorded as a standing requirement.
- [x] **04.2g** Expose a stable unauthenticated instance capability document (for example `GET /api/v1/instance`) reporting the deployment tier, the active degradation identifiers, the available authentication capabilities and `passwordHashPolicy` including its downgraded flag, plus the documented instance limits. Accepted 2026-09-30: `GET /api/v1/instance` is implemented on both profiles with a closed `InstanceDocument` contract — password capabilities advertise only under the standard Argon2id algorithm so the minimum tier's floor-disabled login cannot present itself as usable, passkeys reflect the relying-party configuration, administrator-assisted recovery reflects the staff-enrollment wiring, and `limits.documented` points at the capacity section of [FREE-TIER-PROFILE](../../FREE-TIER-PROFILE.md). Consolidate it into the public OpenAPI in 10.1a. The SPA consumes it through 11.1g and must never imply a capability the instance lacks.

### Step 04.3 — Implement identity and permission management

- [x] **04.3a** Model User and Staff principals separately; keep stable external Staff identities keyed by issuer + subject and explicit audited account linking only. Accepted 2026-10-01 (audit portion resumed by the user's instruction): the modeling is complete and proven — `principals.kind` (user/staff) with the operator-channel Staff enrollment, identities unique per (provider, issuer, subject) so email equality can never link or grant, staff-aware credential/session paths, and local-password Staff handles disjoint from User handles by the global identity uniqueness — and account linking is explicit and audited: passkey registration appends the `account.linked` audit event (metadata kind `passkey`, closed catalog), and the future SSO plugin must reuse the same audited linking contract for `issuer + subject` identities; silent linking is prohibited by the catalog's closed shape.
- [x] **04.3b** Implement project roles/permissions, resource ownership, suspension, and authoritative object-level checks. Never rely on hidden UI controls or stale embedded role claims. Accepted 2026-09-30: the `project_roles` store (grant/replace/revoke/load + administrator anchors) backs a primary-store `AuthorizationFacts` resolver wired into the shared `requireAuthorizedAction` guard; facts always come from current server state (principal kind/status/credential, project visibility/state, membership role, token issuance) — never client claims — and suspension denies tokens and sessions on their next use. The object-level `permissionGranted` hook stands open for module 06's feature predicates, as designed.
- [x] **04.3c** Implement account/profile and authorized role-management APIs with bounded lists, safe public DTOs, audit, and assurance requirements. Accepted 2026-09-30 in its non-audit scope (session listing and owned revocation, project member role grant/replace/revoke and principal suspend/activate under the guarded `role:manage`/step-up requirements) and completed 2026-10-01 in its audit portion (resumed by the user's instruction): every mutation appends its closed-catalog audit event after the authoritative write — `session.revoked`, `role.granted` (with the granted role), `role.revoked`, `principal.suspended`, `principal.activated` — correlated by the response's request id; denied operations append nothing (no enumeration oracle), a missing sink or failed bounded append fails the request with `AUDIT_UNAVAILABLE` (503) without compensating the committed write, and the crash window between write and append is the trail's recorded limit.
- [x] **04.3d** Expose provider contracts for later SSO/CAPTCHA integrations without requiring those plugins for basic Core operation. Accepted 2026-09-30: the CAPTCHA provider contract is implemented (optional complete-binding composition, per-action required verification, single catalogued outbound call, fail-closed provider handling) and the SSO provider contract is specified in [AUTH-FLOWS](../../AUTH-FLOWS.md) (OIDC/OAuth 2.0 client, issuer+subject keying, claim-to-role explicit audited mapping, local authorization engine precedence, no first-party cookie handling); Core operates with zero plugins on both profiles.
