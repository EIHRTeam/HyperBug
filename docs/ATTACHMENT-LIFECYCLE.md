# Attachment upload lifecycle

Module 07's current slice implements shared application services, closed API contracts and D1/PostgreSQL persistence under [ADR 0011](decisions/0011-immutable-attachment-processing.md). No production scanner is configured; default files remain unscanned/quarantined. Actual local ClamAV adapter and dual-profile durable journeys are verified separately from synthetic default tests and production acceptance. Module 09 dispatch and suspended audit work remain incomplete.

## Intent and transaction rules

| Operation | State / accounting outcome | Boundary |
| --- | --- | --- |
| Reserve / exact replay | `pending`; reserve maximum bytes and one pending slot; exact retry counts once | One database transaction/batch; current principal/project/content authorization |
| Request finalize | `pending → uploaded`; public `awaiting-processing`; quota unchanged | One conditional database write; repeat requests idempotent before expiry |
| Claim processing | `uploaded`; persisted UUID lease and expiry, bounded to 300 seconds | Current authorization plus fencing; one concurrent winner |
| Verify immutable final bytes | `uploaded → finalized`; public `quarantined`, `unscanned`; reserved maximum/slot removed and actual bytes added to used | Storage outside transaction; fresh authorization/time and lease fence inside atomic accounting commit |
| Reject size/type/magic/checksum | `uploaded → rejected`; reservation retained | Fenced database mutation; physical cleanup required before release |
| Claim expired cleanup | Unverified states → `expired`; reservation retained | System lease after expiry plus 300-second grace; no User permission needed for owned garbage cleanup |
| Confirm physical cleanup | `reserved → released`; maximum/slot removed once | Delete staging and final keys, confirm absence, then fenced database accounting; retained tombstones permit another sweep |

The internal `uploaded` state records a processing request and does not assert object existence. A finalized retry must match the verified digest/size and cannot change accounting. Unfinished processing requests/commits reject expiry. Leases use live time after storage I/O; expired workers cannot commit or release. Replaying released accounting never changes counters or clears another worker's lease.

Reservations bind principal, project, 256-bit random staging/final keys, safe filename, MIME, maximum size, expiry, and one of `issue-draft`, `comment-draft` with parent Issue, existing `issue`, or existing `comment`. Existing targets have same-project foreign keys. Draft UUIDs do not grant content access. Current visibility, active membership/status, ownership/moderation and deletion are rechecked inside persistent mutations. Reads/capabilities separately authorize the current request and always scope intent retrieval to its owner/project.

Quota is maximum reservations plus actual used bytes, applied independently to the project and global principal across projects. Initial server policy: 32 MiB/file, 10 GiB/project, 1 GiB/principal, 1000/16 pending project/principal slots. A reservation failure rolls back both counters and the intent. PostgreSQL locks project before principal/membership/content and usage/intent rows; D1 guarded batches use chained affected-row predicates and constraint witnesses to abort zero-row preconditions. Storage, signing, hashing and callbacks never run inside those transactions.

Additive D1 `0020_upload_reservations` and PostgreSQL `0019_upload_reservations` preserve historical rows. They seed used bytes from finalized intents and maximum reservations/slots from all other legacy states, including expired/rejected rows whose physical cleanup is unproven. Legacy rows without details are unsupported by the new API/handlers. An operator must reconcile/adopt or physically clean them before releasing their retained quota; no automatic adoption or destructive legacy cleanup is claimed. Safe-integer aggregate constraint failures require operator reconciliation before migration rather than silently dropping accounting.

## API and processing

| Endpoint | Request / response |
| --- | --- |
| `PUT /api/v1/projects/:projectId/uploads/:uploadId` | `{filename, contentType, maxBytes, association}`; explicit retry UUID; 200 reserved/replayed intent |
| `GET .../uploads/:uploadId` | Owner/project/current authorization; 200 intent view |
| `POST .../uploads/:uploadId/capability` | Closed `{}` body; pending intent only; 200 signed staging PUT, Content-Type and expiry |
| `POST .../uploads/:uploadId/finalize` | Closed `{}` body; multipart requires provider completion; 202 awaiting processing or 200 already verified quarantined intent |
| `GET / POST .../uploads/:uploadId/multipart` | Read catalog / create or resume session; closed `{}` POST; 200 session view |
| `POST .../multipart/parts/:partNumber/capability` | Closed `{}` body; 200 short-lived signed part PUT |
| `PUT .../multipart/parts/:partNumber` | `{expectedRevision, etag, sizeBytes}`; 200 updated catalog or exact replay |
| `POST .../multipart/complete` | `{expectedRevision}`; 202 awaiting immutable processing or 200 verified replay |
| `POST .../multipart/abort` | Closed `{}` body; 200 aborted catalog; quota retained until cleanup |

DTOs expose filename, declared/actual size, association, revision, times and truthful state, including awaiting-scan, failed/infected and ready only with bound clean evidence. Scanner metadata/results remain private. They omit raw object keys, principal ID, leases, provider versions, digests and download URLs. Every response is no-store; signer/storage exceptions map to fixed bounded errors. Invalid/expired/conflicting/forbidden/not-found/unavailable outcomes use `UPLOAD_*` codes. Ordinary requests never receive file bodies or run promotion/hash work.

Capabilities expire in at most 300 seconds and never outlive remaining intent lifetime. They are reusable staging-write bearer capabilities; declared size is enforced during final verification, not presumed enforced by signing. Reservation selects and persists direct PUT below the configured threshold (default 8 MiB) or multipart at/above it. Multipart uses uniform server-owned non-final part size (default 5 MiB) and a maximum part count derived from reserved bytes. A smaller actual file is allowed; its last part may be shorter. Direct capabilities are denied for multipart intents.

`processUploadIntent` is an independently callable background handler. A caller supplies current authorization and a persisted fenced lease. It promotes to a create-only final key, validates/hash-streams the actual immutable snapshot and commits quota atomically. Backend intent metadata supports crash resume even after staging overwrite/removal. The canonical immutable identity is final key plus `sha256:<digest>`; provider version remains separately nullable. Verified content stays in intent storage until future atomic Issue/comment/form association. No runtime dispatch is composed, so 202 means awaiting processing, with no queue, running or scan claim.

`cleanupUploadIntent` handles one expired unverified intent with a fixed number of owned-key storage operations. Failure or lease loss retains quota; retry requires a valid lease. Known multipart sessions are aborted before owned objects are deleted. Finalized/used files are deliberately held. `selectCleanup` and `cleanupUploadPage` now select/execute at most 20 project-local candidates per page using internal state/expiry/UUID keysets. They exclude future/grace-period intents, active leases, finalized/used objects and unsupported legacy rows; include released tombstones for repeat late-write removal; and continue after a held candidate. Selection returns only private internal scope/expiry/state, never keys or file bytes. Callers walk the returned cursor to exhaustion and start a fresh sweep to revisit held rows. Limits bound page size and provider concurrency (one candidate); this does not claim a provider-independent hard wall deadline. Verified-unlinked cleanup, legacy adoption, tombstone retention/compaction and scheduling remain incomplete.

## Multipart consistency and crash recovery

| Transition | Preconditions and accounting |
| --- | --- |
| `planned → creating` | Current authorization, pending/live intent, one persisted lease winner; reserve unchanged |
| `creating → active` | Register provider identity with the creation lease; backend bookkeeping survives permission loss, then public return reauthorizes |
| `active → active` | Part receipt uses current catalog revision; exact receipt retry is idempotent, conflicting stale receipt fails |
| `active → completing` | Catalog must start at part 1, be contiguous, have uniform non-final sizes and fit reserved bytes; lease freezes catalog |
| `completing → completed` | Actual staging identity, backend intent metadata, MIME and byte count must match; live authorization/lease commit records awaiting processing |
| `planned/active/completing/completed → aborting → aborted` | An active competing lease prevents abort; abort makes content rejected and retains reservations |
| Any known unverified session → expired cleanup → `aborted` | Abort provider session, delete both owned keys, confirm absence, release once with cleanup lease |

D1 **0021_upload_multipart** and PostgreSQL **0020_upload_multipart** add same-project session rows atomically with reservations. Sessions contain private provider IDs, bounded JSON part arrays and revisions. They leave existing direct/legacy rows without a session and preserve quota accounting. Receipt mutations and state/lease changes commit together; D1 uses revision/intent/lease/authorization CAS plus a constraint witness, while PostgreSQL uses the project-first locked transaction. No provider I/O occurs in these transactions.

Receipts remain client claims. Completion invokes the provider with the frozen ETags and checks actual completed staging metadata/size without buffering or hashing in the ordinary API. Background immutable processing still checks magic bytes where supported, hashes final bytes and commits actual used quota. A reusable signed part URL can replace staging parts before completion; it cannot write the final key. Resume returns receipts, sizes, ETags and catalog revision, never raw provider identity or object keys. Direct and part issuance both recheck current permission, persisted state and live expiry after signing; a capability completed after revocation/finalization/expiry is withheld.

A crash after provider completion but before database completion can recover by inspecting the owned staging object's backend-authored `intent-id` metadata; mismatched objects are rejected and retain quota. A crash during creation before its provider ID is saved is ambiguous: another create is denied, cleanup keeps quota and owned objects, and explicit provider discovery/reconciliation is required. The native BlobStore has no discovery operation. An optional trusted `UploadMultipartReconciler` can exhaust exact-owned-key discovery, abort every matching provider session and confirm zero remaining uploads. Core bounds its callback to 30 seconds, validates a closed exact-key absence proof and rechecks the cleanup lease before deletes/quota release. The ambiguous creating marker is retained even after quota release, so every later tombstone sweep repeats discovery and can catch late provider creation. Missing/failed/truncated/wrong-key/stale proof retains quota and owned objects. Both selected storage compositions now supply the bounded discovery adapters described below; unconfigured or failed discovery still retains quota. Core callback tests are synthetic, with actual S3-provider discovery evidence recorded separately. R2 S3 ListMultipartUploads is documented as available, providing a concrete operator-adapter path; its native Workers binding does not supply that method. Known failed creations attempt provider abort and persist the compensated state under their lease. Scanner/release and Module 09 dispatch are separate incomplete work.

## Scanner/result and release hooks

`AttachmentScanner` is a trusted injected hook, not a client callback. `scanVerifiedUpload` is independently callable background processing with no default scanner or runtime dispatch. Missing scanner returns unavailable before any claim and preserves `unscanned`/`quarantined`. Scanner adapter/plugin configuration and actual malware-detection acceptance remain incomplete.

| Transition | Required evidence and policy |
| --- | --- |
| Finalized/used → scan pending | Current authorization, immutable identity, unique persisted attempt lease; quarantine and used bytes retained |
| Pending → clean result | Complete scanner stream consumption, exact canonical byte count/SHA-256, bounded engine/version/signature metadata and live attempt lease; remains quarantined |
| Clean/quarantined → ready | Separate current-authorized conditional release; same attempt, immutable identity and current `attachment-scan-1` policy; lease cleared |
| Pending → infected | Verified complete immutable stream plus infected verdict; rejected, used quota retained |
| Pending → failed | Timeout, unavailable, partial consumption or malformed result stays quarantined; identity mismatch is rejected; used quota retained |
| Expired scan lease → new attempt | New token fences late results; cannot reuse the prior attempt ID; policy change re-quarantines before result replacement |

Core streams the final object through its incremental digest as the scanner consumes it. An early clean return, incorrect metadata, different final bytes, invalid/extra result fields or unconsumed stream cannot release content. Work has a 60-second maximum wall timeout (bounded by the persisted lease), cooperative abort and late-result discard. No provider/scanner work occurs in a database transaction. Clean result commit and release are separate steps; a crash or permission loss between them leaves clean-but-quarantined content and supports a fresh authorized release retry. Neither signature metadata nor a hash alone establishes malware detection; the trusted scanner must actually supply the verdict.

D1 **0022_upload_scans** / PostgreSQL **0021_upload_scans** add one mutable latest-result row bound to project/intent/attempt, canonical digest/size, policy, timestamps and bounded evidence. This is operational policy data, with no audit history. The migrations quarantine unsupported legacy ready/scan claims, remove unproven scan labels and increment intent revision while preserving immutable identity and used quota. Database guards forbid ready without a matching completed clean result, prohibit changing that result while ready, and prevent verified identity mutation. PostgreSQL retains project-first locking; D1 CAS batches roll back result/intent/lease changes after authorization races. Older migrations are unchanged; no shared/cloud application is claimed.

Public DTOs report pending/clean/infected/failed truthfully, omit private engine/signature evidence, and withhold ready when the current policy/result identity is missing. No public scan/release endpoint is exposed. Synthetic tests exercise clean/infected outcomes and guard behavior; they are not evidence that any actual upload was scanned or safe to release. Actual scanner integration is required before **07.3f** acceptance. Isolated delivery and verified-file cleanup remain separate Module 07 work; guarded form consumption is described below.

## Trusted local ClamAV adapter (2026-10-04)

`apps/api-node/src/attachment-scanner.ts` is an independently callable trusted `AttachmentScanner`; `configureNodeAttachmentScanner(file)` returns null without an explicit mount. It is not wired into Node startup, Workers, public routes or Module 09 dispatch. Invalid selection returns the fixed `Invalid attachment scanner configuration` error. The configuration file uses the existing mode-0400/0600 owned, no-symlink secret-file reader with a five-second caller deadline. Its exact JSON fields are `executable`, `executableSha256`, `sigtool`, `sigtoolSha256`, `certificateDirectory`, `certificateSha256`, `databaseDirectory`, `temporaryDirectory` and `maxSignatureAgeMs`. Paths are absolute; executable, sigtool and certificate pins are lower-case SHA-256. This initial adapter supports POSIX Linux/macOS only.

Engine/verifier assets must be regular root/operator-owned files without group/other write permissions. Database and certificate directories/files must also have every write bit disabled; snapshot entries cannot be symlinks. The database directory contains exactly official `daily.cvd`, `main.cvd`, `bytecode.cvd` and their matching versioned detached `.cvd.sign` files. No custom rules, freshclam state or extra files are permitted. The certificate directory contains only the pinned `clamav.crt`. Startup runs CVD information/integrity and independent detached-signature verification, then derives bounded engine/signature evidence from actual verified metadata. A required daily freshness limit is at most 48 hours, with only five minutes of future-clock tolerance. Initialization has a 30-second asynchronous caller deadline and each verification command a 15-second process deadline. Snapshot updates require a newly verified read-only snapshot and new instance; this adapter starts no updater.

Every scan checks asset inode/device/size/time/mode/owner and directory membership before and after the process, plus current daily freshness. An owned mode-0700 temporary base is checked by inode/device/mode/owner before creating a private scan directory. One physical scan process is admitted per instance with no queue; excess calls fail unavailable. The producer sends one chunk/write callback at a time under a 32-MiB input cap and exact byte count. There is no shell or inherited parent environment; only locale and certificate-path settings are supplied (macOS can synthesize its own CoreFoundation locale variable). Combined stdout/stderr is limited to 8 KiB and never logged or returned as public evidence.

The process has a 60-second outer deadline and caller cancellation. It receives TERM for its detached POSIX process group, followed by KILL after 300 ms when still alive. A returned timeout is separate from actual child/stdio closure: admission stays occupied through process reaping and temporary cleanup, and `close()` aborts then awaits that work. Cleanup failure closes admission and denies a successful outcome. Empty producer chunks fail partial rather than enabling a zero-byte progress loop. ClamAV receives 128-MiB expanded per-file/PCRE/aggregate scan, 100-file, depth-8, 10-second internal scan-time and PCRE work limits, with encrypted/broken/exceeded-limit alerts; external input stays capped at 32 MiB. Only the exact complete `stdin: OK` exit-0 protocol is clean; complete bounded exit-1 detection carries verified evidence. Encryption/limit/broken heuristic detections map to failed/partial. Incomplete input, unexpected output, failure or snapshot drift never yields clean.

An actual nested-ZIP probe exposed a ClamAV 1.5.4 behavior absent from the returned documentation: its extractor can truncate a member at `maxfilesize` without an alert. A draft 32-MiB per-file / 128-MiB aggregate configuration returned clean for a 33-MiB member. The current per-file cap matches the aggregate cap so truncated output cannot fit the remaining budget after its container is counted. Actual 33-MiB supported, 129-MiB over-budget and 101-file archive probes verify this selected path. This is bounded compatibility evidence for those fixtures, not exhaustive archive-format or scanner coverage. The original aggregate expansion budget remains 128 MiB; the draft is not an accepted security baseline.

These are application/engine limits, not OS memory/CPU/network/process isolation. Filesystem waits cannot be physically canceled by this wrapper, and asynchronous deadlines cannot preempt blocked synchronous execution. One instance cannot coordinate another independent scanner instance. Production deployment must supply resource isolation, outbound restrictions, coordinated admission and an update/rotation procedure; no such deployment is claimed. Core still owns full immutable digest/size consumption, current authorization, fenced result persistence and separate release. The trusted transport below and actual local durable pipeline evidence cover both database profiles, while 07.3f production acceptance remains incomplete. [Actual-engine evidence](plan/evidence/07-scanner-environment-validation.md) distinguishes these lanes from synthetic/default regression and deployment.

## Isolated authorized media (2026-10-04)

The optional exact `HYPERBUG_MEDIA_ORIGIN` arms a separate origin surface at `GET/HEAD /attachments/:attachmentId`, with narrow OPTIONS preflights. It requires the configured blob/attachment/issue/authorization stores and a hostname distinct from browser origins, registered client redirects and the passkey origin, including different ports on the same hostname. Production requires HTTPS; only explicit local loopback HTTP is allowed. Absent configuration disables delivery. Requests on the media hostname, including scheme/port/trailing-dot aliases, never fall through to authentication or business routes. Query strings, arbitrary paths, non-GET/HEAD methods and multiple/malformed byte ranges are refused. No auth cookies, token endpoints, signed download URLs or redirects exist on this surface.

A ready attachment must match its consumed issue/comment association, project, finalized/used intent, immutable key/digest/size/type/version and current completed clean scan. The server rechecks current project visibility, bearer validity, active principal/Staff membership, visible non-deleted parent and the shared read permission. Private content is invisible to anonymous callers, cookies and nonmembers; archived projects remain readable. Comment delivery additionally requires its visible non-deleted issue. Attachment snapshot and authorization are checked again after storage acquisition, before any bytes are returned; denial cancels the acquired stream. Linking or an opaque attachment ID grants no private access.

Every file, including HTML, SVG, XML and scripts, returns `application/octet-stream`, `Content-Disposition: attachment` with a sanitized ASCII fallback and encoded Unicode filename, `Cache-Control: no-store`, `nosniff`, sandbox CSP, no-referrer and same-site resource policy. Single authorized byte ranges return 206; malformed/unsatisfiable ranges return 416 with the total size only after authorization. HEAD has the same checks and safe headers without file bytes.

Storage acquisition is bounded to five seconds; database operations use existing one-second deadlines. Streams pull one chunk at a time, enforce the exact promised length, cancel on caller disconnect, and have a 30-second idle-read and five-minute total deadline. A late acquisition is canceled, not exposed. Post-header stream errors terminate delivery rather than returning a successful truncated body. Authorization is rechecked before delivery, not continuously after each already-sent chunk. Telemetry uses the fixed `attachment.media` label and response request ID, never file content, raw paths, tokens, keys or provider/scanner exceptions.

The PostgreSQL proof uses certificate-verified local HTTPS over a native TCP connection with an explicit virtual media Host. This proves the local transport and both database policies, not DNS, a browser journey, installed production CORS or deployment. Synthetic clean results exercise delivery guards; they remain separate from actual scanner acceptance.


## Explicit-policy verified-unlinked cleanup (2026-10-04)

`selectOrphanCleanup`, `cleanupOrphanUploadPage` and `cleanupOrphanUploadIntent` are separate internal ports/handlers for supported used uploads without any attachment row. The trusted caller must supply `retainAfterExpiryMs` (a safe duration at least the existing 300-second capability grace); there is no default retention value, public route or runtime scheduling. The project-local expiry/UUID keyset returns at most 20 candidates with one look-ahead row. Future/too-young records, live competing leases, linked attachments (including hidden/deleted parents) and unsupported legacy rows are excluded. Claims repeat attachment absence and lease/revision predicates atomically: D1 uses a CAS batch with a NOT NULL rollback witness; PostgreSQL uses the existing project-first lock order.

Claiming marks policy deleted and increments revision while preserving finalized state, verified identity and used quota. Existing immutable-state guards remain intact. New form consumption and scan/release transitions cannot revive the retired snapshot. A failed delete, remaining object, incomplete multipart discovery or lost lease leaves used bytes retained. Multipart orphans require complete exact-key reconciliation on every sweep, including released tombstones. Only after deleting both owned keys and confirming absence may the fenced repository transaction decrement actual used bytes from project and global-principal counters exactly once. Missing/invalid counters roll back the whole release. A stale token cannot clear a newer lease.
