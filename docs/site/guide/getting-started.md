# Get started

[Documentation home](../index.md) · [Issues](issues.md) · [Accounts](accounts.md)

HyperBug is a public feedback and issue tracker. You do not need a Git repository or code-hosting account to read public feedback. This manual describes the locally verified candidate; it is prepared but unpublished, with backend and release gates still open.

## Find a project

Open the project link shared by its team, or enter its complete project ID on **Overview**. There is no public project directory/search API in this candidate. A private project requires the appropriate identity and membership; a denied or unavailable page does not reveal its content. Archived projects retain readable history but reject changes.

Open the project’s Issue list. Search with words or documented filters and follow page links; the URL preserves the query/page for sharing and back/forward navigation. Minimum instances search titles only, Standard searches titles and bodies; comments are not indexed. The instance page reports the active tier and unavailable capabilities.

## Report and discuss

1. Read existing feedback first. Sign in through **Account → Sign in** when you need to participate; credentials and consent stay on the authorization service.
2. Choose **New issue**, select a template or Issue Form, write a clear title and complete required fields. Preview content before submitting. Uploads may need processing/scanning before they can be used; uploading alone does not release a file.
3. Submit once. If the response is uncertain, retry the unchanged submission so its receipt can reconcile it without duplication. Review a changed form/revision before trying a different payload.
4. Follow the Issue detail link, comment or react where permitted, and use timeline pagination/permalinks to revisit discussion. Staff can label, assign, change type/milestone and close/reopen according to their roles.

Drafts and app tokens stay in page memory. Navigation, reload, expiry, sign-out and permission loss can clear drafts. Preserve your own text safely before leaving; never put credentials or unnecessary private information into public feedback. Reloading requires another top-level sign-in, which can reuse the authorization service’s separate first-party session.

## Understand current availability

Public feedback, forms, safe Markdown, attachments, search, triage, audit browsing, public API and plugin foundations pass their recorded local scopes. Hosted backend acceptance and production scanner/proxy/provider validation remain separate. Relations, saved views, subscriptions, notifications, bulk/import/export and named integrations are later modules; AI and realtime collaborative editing are deferred.

See [the issue guide](issues.md) for upload/conflict recovery, [accounts](accounts.md) for access/passkeys, [project management](project-management.md) for Staff actions and [troubleshooting](troubleshooting.md) for safe diagnostics. [Release notes](releases.md) state the exact prepared/unpublished outcome and known limitations.
