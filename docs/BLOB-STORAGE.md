# Portable blob storage

Module 07's internal `BlobStore` and `BlobAuthorization` ports are defined in `packages/application/src/blob-store.ts`. `@hyperbug/blob-r2` implements native Workers binding CRUD/multipart and a separate Web Crypto S3 signer; `@hyperbug/blob-s3` implements Node 24 CRUD/multipart and signing with AWS SDK v3. No SDK types enter domain/application contracts. Both composition roots now optionally supply them to the shared upload-intent API; see [attachment lifecycle](ATTACHMENT-LIFECYCLE.md).

## Object and stream rules

- Keys are opaque random 256-bit identifiers: `staging/<64 lowercase hex>` and backend-only `objects/<64 lowercase hex>`. Filenames are never key components.
- Direct PUT and multipart signing only accept staging keys. Final-key writes require create-if-absent; multipart cannot address final keys. A signed staging PUT remains reusable until expiry.
- Every backend write has an explicit byte length and a pull-based stream. The shared length guard holds the final producer chunk until EOF, rejects both short and surplus data, and propagates cancellation. R2 receives a native `FixedLengthStream`; Node aborts its HTTP request when the source fails. No ordinary upload route buffers files through the API.
- PUT accepts an optional SHA-256 hex digest. R2 validates it natively; Node incrementally hashes the stream before forwarding the final chunk and also sends the checksum header. ETags are opaque validators, not cryptographic digests or immutable version identities.
- GET returns the metadata of its actual snapshot; `size` is total object size and `bodySize` is the delivered size, including ranges. The stream enforces delivered byte count. R2's opaque version is recorded; S3's version is nullable. No release decision uses a subsequent HEAD paired with an earlier body.
- MIME values are bounded lowercase media types without parameters. Custom metadata has at most 16 ASCII entries and 1,024 combined characters; avoid identities, capabilities and private filenames in object metadata.
- Provider errors become bounded internal error codes, without raw SDK messages, credentials or URLs. Expected streaming failures may produce the SDK's generic non-retryable-request warning; no sensitive payload is included.

## Multipart and temporary capabilities

Adapter configuration owns threshold, minimum/maximum part size and maximum part count. The portable provider floor is 5 MiB for non-final parts, with at most 10,000 parts and a 5 GiB maximum part. Product attachment limits and reservation policy remain separate. The test policy uses an 8 MiB threshold, 5 MiB minimum, 64 MiB maximum and 100 parts; the initial operator defaults use the same values, with a separate 32 MiB file quota. Reservation persists direct transfer below the configured threshold and a uniform multipart plan at/above it. Shared APIs provide owner-scoped create/resume, bounded part capabilities/receipts, fenced complete/abort and known-session cleanup; actual immutable processing remains a separate background handler.

Persist `(key, uploadId)` for resume/cleanup. Part replacement is possible before completion. Complete accepts an ordered contiguous part catalog starting at 1; providers enforce their size rules, including R2's equal-size non-final parts. Both bare native and quoted S3 ETags are accepted; the R2 adapter normalizes them for native completion. Abort is idempotent. Completion hydrates staging metadata and checks its returned ETag; it never establishes release or immutable identity. Intent expiry and single-intent physical cleanup are implemented. Persisted multipart catalogs and known-session abort cleanup are implemented; bounded project-local expired selection/page execution and an optional trusted reconciliation hook are implemented; both selected profiles now supply bounded unknown-session discovery; legacy/adoption/tombstone-retention cleanup and dispatch remain incomplete; Module 09 scheduling is held.

Capabilities expire in at most 300 seconds. PUT signs Content-Type explicitly. Download signing accepts only final keys and a forced attachment disposition with a bounded ASCII fallback filename. The application must authorize a released attachment before invoking it. A bare S3 capability cannot supply the complete isolated media-origin/nosniff policy; the authorized media handler streams from the adapter without invoking download signing (see [lifecycle](ATTACHMENT-LIFECYCLE.md#isolated-authorized-media-2026-10-04)). Signers never configure storage CORS implicitly or treat CORS as authorization.

R2 signing requires backend-only bucket-scoped S3 credentials, distinct from Wrangler OAuth used for management/bindings. Production endpoint configuration requires HTTPS. Only an explicit local-test option permits HTTP on loopback; credentials in endpoint URLs are rejected. Public API responses/logs must not expose configuration or reusable private capabilities unnecessarily; the current upload routes have no-store/redacted DTO/error/log checks; download authorization and redaction are verified by the separate media checkpoint; synthetic scan/release evidence never proves actual scanning.

- `pnpm test:node`: Node S3 adapter against Miniflare's local S3 emulator; the real-service tests explicitly skip without their binary setting.
- `HYPERBUG_TEST_SEAWEED=/absolute/path/to/weed pnpm test:storage:real`: isolated real SeaweedFS 4.48 on loopback, random bucket-scoped credentials, private temporary data, dynamic ports, no telemetry, process/data cleanup. The command fails when the setting is absent; it never silently substitutes an emulator or downloads/installs a server.

The compatibility suite also tests actual signed PUT/GET/UploadPart, signature/header/query/key tampering, response disposition and an independent bad SHA-256 request sent directly to the real service. This does not establish support for other S3 providers, cloud deployment, browser CORS or public attachment APIs.

The shared `promoteStagingBlob` background primitive streams staging into a create-only server-owned final key, then hashes and validates the actual final snapshot (size/type/practical magic/filename). Backend-authored intent metadata binds ownership. It resumes from the existing immutable final object after staging overwrite/removal or a crash. It always returns `unscanned` and never releases an attachment. Callers must first authorize and acquire a persisted lease/reservation; validation failures retain owned objects for explicit cleanup. Ordinary synchronous finalize APIs must not run large hashing.

Actual R2 is also exercised with `HYPERBUG_TEST_R2_CONFIG=/absolute/path/to/private-config.json pnpm test:storage:r2`. The ignored mode-0600 JSON file contains `accountId`, the existing test `bucket`, and `credentialsFile`; that separate private file contains `accessKeyId`/`secretAccessKey`. Use a test bucket and scoped backend credentials, never production data. The suite uses random owned keys and deletes those keys; it never deletes the bucket or changes CORS. It proves both signers on actual R2 under local Node execution. Local workerd/remote-binding signer and promotion checks and exact R2 CORS protocol evidence are recorded separately. No browser or product deployment acceptance is inferred.

Remaining Module 07 work: deployment-specific exact CORS, actual scanner acceptance, deployment/browser media acceptance, legacy/adoption/tombstone-retention cleanup and dispatch. Intent/quota persistence, direct/multipart capabilities and catalogs, manual background promotion and expired-unverified physical cleanup are implemented; local lifecycle evidence is recorded separately from prior actual-provider compatibility. Do not release objects based on staging HEAD or a client claim, infer scanning from upload success, or resume suspended audit work.

### Native Workers discovery refinement (2026-10-04)

Native R2 bindings still provide CRUD/multipart and expose no session-listing method. A separate reviewed dynamic S3 operation contract permits only header-signed GET ListMultipartUploads and DELETE AbortMultipartUpload at the fixed operator-selected R2 account/bucket endpoint. Core supplies the exact opaque staging key and validated bounded continuation/session IDs. URLs, hostnames and keys cannot come from public client input. Credentials remain in headers, redirects are manual and every 3xx response is rejected, cache mode is no-store, and `AwsClient.sign` plus native fetch avoids the client's automatic retries. XML is read one chunk at a time with a 128 KiB cap, depth 8 and 1,024 nodes; DTD/custom entities, malformed UTF-8/structure, mixed content, ambiguous fields and invalid ownership fail closed. Late responses and stalled bodies are canceled under the shared 30-second total deadline. A noncooperative provider cannot extend the caller wait, though cancellation cannot guarantee that an external mutation never finishes late; tombstones therefore retain reconciliation state.

### Approved historical S3 recovery (2026-10-04)

`createS3LegacyRecoveryProvider(config, approval)` is an internal one-decision capability separate from BlobStore/current-key reconciliation. Its fixed endpoint/bucket/region/path-style configuration and closed ownership/accounting manifests must match the original bounded UTF-8 bytes and SHA-256 references in the canonical historical decision. Original bytes matter; reserialization requires a separately reviewed decision. Hashing or constructing manifests never establishes the truth of their claims. Use the atomic recovery ledger claim before physical work and its fenced release afterward. There is no public route, raw client, arbitrary-key method, implicit adoption or scheduler.

Ownership JSON has exactly `version: "s3-legacy-ownership-1"`, `endpoint`, `bucket`, `region`, `forcePathStyle`, `multipartContinuation` and `snapshot`. Accounting JSON has exactly `version: "s3-legacy-accounting-1"`, the same `snapshot`, and `retained` with the expected `reservedBytes`, `usedBytes` and `reservedCount`. Each original manifest is at most 16 KiB. Destination and decision are copied at construction; later caller mutation cannot retarget them. Ordinary BlobStore keys remain unchanged. Empty/dot/backslash historical path segments remain unsupported.

Default `multipartContinuation: "s3"` allows only the existing exact-key upload-ID-only compatibility case; a mixed-prefix page without NextKeyMarker fails closed. Explicit `"seaweedfs-4.48"` mode is bound into ownership evidence and covers the pinned provider's upload-ID ordering across mixed prefix siblings. Both modes validate at most five 20-row pages per discovery, markers belonging to returned rows, duplicates and bounded Unicode/session IDs. Full discovery precedes abort, only exact-key sessions are aborted, prefix siblings survive, and a second complete discovery establishes session absence.

The provider checks elapsed explicit retention, one operation at a time, a shared 30-second deadline and cooperative cancellation. A low-priority SDK deserialize middleware bounds every HTTP body to 128 KiB before XML parsing, rejects unexpected encoding, and recognizes only explicit empty VersioningConfiguration XML for never-versioned status. It checks versioning before mutations and after exact-key DELETE/HEAD and multipart absence. Enabled/Suspended/unknown/unsupported versioning, unsuccessful HEAD absence or any provider uncertainty retain quota. Known R2 endpoints are refused before I/O: the published table marks GetBucketVersioning unsupported, even though this test endpoint returned an undocumented empty response. Generic HEAD-null never proves absence of historical versions.

Real isolated SeaweedFS 4.48 physical recovery and actual R2 refusal/preservation are recorded in [lifecycle evidence](plan/evidence/07-upload-lifecycle-validation.md#fixed-s3-legacy-physical-recovery-2026-10-04). Manifests refer only to newly created owned fixtures; accounting is a test claim, separate from the dual-store ledger's synthetic proofs. No existing production legacy record is repaired or accepted. R2/native physical recovery, reviewed real accounting/ownership, versioned or ambiguous-key recovery and quiescence/compaction remain incomplete. The fixed response/page/wait bounds do not claim provider-side catalog scanning or global concurrency bounds.
